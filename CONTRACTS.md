# spool data contracts (v1)

Every layer communicates only through these files inside a per-spool **workdir**
(conventionally `<project>/spool/<slug>/`). If you change a format, bump it here first.

> **Editing published spools** is a separate cross-component contract (CLI source
> upload, web jobs API, Fly render worker): see [docs/EDIT-CONTRACT.md](./docs/EDIT-CONTRACT.md).

> **Plan Spool lifecycle and permissions** — the states a plan spool holds, the legal
> transitions, and which requester may call which endpoint in which state: see
> [docs/PLAN-SPOOL-LIFECYCLE.md](./docs/PLAN-SPOOL-LIFECYCLE.md). Every `/api/plans/*`
> route authorizes through the one shared layer described there. The `plan.json` and
> evidence-descriptor formats get their own sections here once R1 lands.

## Workdir layout

```
spool/<slug>/
├── steps.mjs            # authored (scripted) OR generated by `spool live` (the demo script)
├── plan.json            # OPTIONAL: makes this a Plan Spool (see "plan.json" below)
├── vo/
│   ├── manifest.json    # written by `spool vo`
│   ├── seg_00.wav       # 24kHz mono, loudnormed -16 LUFS
│   └── seg_00.words.json
├── video.webm           # written by `spool record` / `spool live` (raw Playwright capture)
├── timeline.json        # written by `spool record` / `spool live`
├── console.jsonl        # browser telemetry captured during recording
├── signals.jsonl        # what the session did, on the video clock (the cut is derived from this)
├── timeline.prev.json   # written by `spool recut` (the cut it replaced)
├── keyframes/step_NN.png # written by `spool live` (one per step; scripted path uses share/frames)
├── video.mp4            # written by `spool render` (normalize pass, CFR 30fps H264)
├── final.mp4            # written by `spool render` (the deliverable)
├── plan.json            # Plan Spools only: the semantic plan (see "Plan Spools")
├── evidence.json        # Plan Spools only: evidence descriptors
└── plan.script.json     # Plan Spools only: generated narration outline (`spool plan generate`)
```

`plan.json` and `evidence.json` are **optional**. A workdir without `plan.json` is an
ordinary spool and behaves exactly as it did before Plan Spools existed.

## Two authoring paths

- **Live** (recommended when you just drove the flow): `spool live <dir>` records the app
  as you drive it once over an HTTP control port, then emits the same `video.webm` +
  `timeline.json` output plus a **generated `steps.mjs` snapshot**. Finish with
  `spool finish <dir>` (or `spool build <dir>`, which detects a recorded session).
- **Scripted** (reproducible): author `steps.mjs` by hand, `spool dry` to debug the driver,
  then `spool build`. The live snapshot is a valid scripted `steps.mjs`, so a live take can
  be edited and rebuilt deterministically.

## steps.mjs (authored per spool)

```js
export const config = {
  url: "http://localhost:4747",            // required
  viewport: { width: 1600, height: 900 },  // optional, this is the default (16:9 fills the rendered frame best)
  title: "Finishing Lab walkthrough",      // optional, used for title card
  format: "wide",                          // optional, "wide" (1920x1080, the default) | "vertical" (1080x1920)
  storageState: "auth.json",               // optional, PATH to a Playwright storageState file (never inline cookies)
  // optional: runs before step 0, recorded but not narrated (login, seeding)
  prep: async (page, h) => {},

  // vertical only, all optional (see "Vertical format" under Render layer inputs)
  hook: "Your diffs explain themselves now",                       // title card, <= 7 words; defaults to `title`
  cta: { text: "See the full walkthrough", url: "spoolkit.dev" },  // end card; defaults to a generic line + `url`'s host
  music: "uplift",                         // "uplift" | "calm" | "none" | path to an audio file
};

export const steps = [
  {
    name: "open-board",                    // kebab-case id, unique
    chapterId: "context",                  // optional, Plan Spools only: the plan chapter this step explains
    narration: "Here's the finishing lab — every rep gets tracked on this board.",
    zoom: "none",                          // "none" (default) | {selector} | {x,y[,scale]} | "auto" (aims at this step's clicks)
    run: async (page, h) => {
      await h.click("text=Start");
      await page.waitForSelector(".board");
    },
  },
];
```

Helper API passed as `h` (implemented in src/record/cursor.js):
`h.move(x,y)`, `h.click(selectorOrPoint)`, `h.type(selector, text)`, `h.hover(selector)`,
`h.scroll(dy)`, `h.pause(ms)`. All produce smooth, human-speed motion and are logged.

Pipeline: `spool build` runs **vo and record in parallel** (record no longer waits
on VO), then render, then share. The capture is at natural interaction speed; the
renderer retimes each step to fit its narration (see "Render layer inputs").

## vo/manifest.json (spool vo ‖ spool record, → spool render)

```json
{
  "engine": "openai",
  "voice": "alloy",
  "segments": [
    {
      "i": 0,
      "name": "open-board",
      "narration": "Here's the finishing lab — every rep gets tracked on this board.",
      "wav": "vo/seg_00.wav",
      "words": "vo/seg_00.words.json",
      "duration": 4.32
    }
  ]
}
```

`seg_NN.words.json`: `[{ "word": "Here's", "start": 0.0, "end": 0.31 }, ...]`
(times are local to that segment's wav; seconds, float).

## Hosted VO API (`SPOOL_ENGINE=hosted` → `POST {host}/api/vo`)

The hosted engine lets a CLI user generate voice with no OpenAI key of their own — the
web app calls OpenAI (gpt-4o-mini-tts + whisper-1) on the server. Auth reuses the
`spool publish` bearer token (per-user `spk_` token or the legacy global token).

Request: `POST {host}/api/vo`, `Authorization: Bearer <token>`, JSON body:

```json
{ "text": "narration for one step (≤ 1200 chars)",
  "voice": "alloy",                       // optional, defaults to the CLI's default voice
  "instructions": "voice-direction (≤ 2000 chars)" }   // optional
```

Response `200`:

```json
{ "audio": "<base64 wav>",               // raw gpt-4o-mini-tts wav (NOT loudnormed)
  "words": [{ "word": "Here", "start": 0.0, "end": 0.34 }],  // whisper-1 word times, local to the raw wav
  "usage": { "remainingToday": 297 } }
```

The CLI writes the wav, runs the **same local loudnorm** pass as the direct engine, and
(when the tempo is not 1) applies `atempo` locally and scales the returned word times by
`1/speed` — so timing truth is identical to the direct OpenAI path. Errors: `401`
(bad/missing token), `400`/`413` (missing/oversized `text`), `429` (per-user daily cap,
env `VO_DAILY_CAP`, default 300 — the JSON `error` carries the message), `502` (upstream
TTS failure). Node runtime; a ~10s wav base64 is ~1–2MB, within the function body cap.

## timeline.json (spool record → spool render)

```json
{
  "version": 1,
  "title": "Finishing Lab walkthrough",
  "url": "http://localhost:4747",
  "viewport": { "width": 1600, "height": 900 },
  "fps": null,
  "video": "video.webm",
  "steps": [
    {
      "i": 0,
      "name": "open-board",
      "chapterId": "context",
      "start": 1.02,
      "end": 2.31,
      "zoom": "auto",
      "clicks": [ { "x": 512, "y": 340, "t": 1.60 } ]
    }
  ],
  "total": 8.7
}
```

- All times in **seconds relative to video t=0** (context/page creation), at
  **natural interaction speed** — steps are not padded to the narration anymore.
- `steps[i].end` includes a short post-step settle so the step's final UI state is
  painted and captured (the renderer freeze-holds that last frame).
- `clicks[].t` is when the click fired; coords are viewport CSS pixels.
- No `voDuration` field: VO is produced in parallel and the renderer retimes.
- `steps[i].narration` is present on **live/recorded** sessions (v1-compatible additive
  field) so the session is self-describing; `spool finish` reads it if the `steps.mjs`
  snapshot is missing. Scripted `spool record` omits it (narration lives in `steps.mjs`).
- `chapterId` is optional and **Plan Spools only**: the plan chapter this step explains
  (`context` | `outcome` | `approach` | `risks` | `decision`; see "Plan Spools" → "Chapter
  mapping"). It is additive and independent of `name`, which keeps its meaning everywhere.
  A step may carry none, and several steps may carry the same one. An unknown value is
  rejected at authoring time, never written.
- `retimed: true` is an optional top-level flag meaning the times ARE the output clock:
  the renderer must use them unchanged rather than fitting each step to its narration.
  Only a packet video sets it (`src/packet/video.mjs`), because a packet is authored
  beat by beat with no capture to fit anything into, and padding those windows would
  report times the rendered file does not have. Every recorded take omits it.
- `cursor` is an optional top-level `[{ t, x, y }]` motion track (same clock and CSS-pixel
  coords as `clicks`), written **only** when `SPOOL_CAPTURE=cdp` and `SPOOL_CURSOR=render`
  are both set: the in-page overlay is hidden and the renderer redraws the cursor at output
  fps from this track. Off by default (the interpolated motion reads tweened; the default
  baked overlay keeps its recorded character). Its presence is what tells the renderer to
  draw a cursor: takes without it have one baked into the video.
- **OS target** (`spool live --target os`) sets `target: "os"`, `video: "capture.mp4"`
  (already CFR H264 — `normalize` remuxes it instead of re-encoding), `viewport` = the
  capture pixel dims (arbitrary, not 1600x900; the renderer letterboxes it onto the card),
  and a `capture: { device, input:{width,height}, fps }` block. There's no `url` and no
  `page` driver. A step's `zoom` is `"none"` (default) or `{x,y[,scale]}` in **capture-pixel
  coords** (the renderer uses it like a click point); `clicks` is `[]` unless a zoom point is
  given, in which case it carries that single point.

## Live control protocol (spool live → HTTP control server)

`spool live <dir> [--url <u>] [--title <t>] [--format wide|vertical]` boots the same recording context as
`spool record` (recordVideo, fake cursor, `console.jsonl` telemetry), navigates to the URL
(from `--url` or an existing `steps.mjs` config), and serves a JSON control API bound to
**127.0.0.1** on an **ephemeral** port. It prints exactly one machine-readable line to
**stdout** and a human usage hint to **stderr**:

```
{"port":64639,"session":"/abs/path/to/dir"}
```

Endpoints (JSON in/out; page ops are serialized so requests can't interleave):

| Method + path | Body | Returns |
|---|---|---|
| `POST /step` | `{ name, narration, zoom?, chapterId? }` | `{ ok, index, name, chapterId?, url }` — closes the previous step (250ms settle) and opens a new one. **`narration` is required** (the renderer fits the window to it). `zoom` defaults to `"none"`; pass `{selector}` to frame the thing the narration is about (resolved to a box at step close, and to `"none"` if it does not resolve), `{x,y[,scale]}` for capture-pixel coords, or `"auto"` to aim at this step's clicks. |
| `POST /js` | `{ code }` | `{ ok, result?, error?, url }` — runs `code` as the body of `async (page, h) => { … }` with the session `page` and the `h` helpers in scope. An error returns `ok:false` and does **not** kill the session (fix the selector and retry). Only successful snippets enter the snapshot. |
| `GET /status` | — | `{ ok, url, elapsed, completed, current }` — current step index/name, elapsed seconds, url. |
| `POST /end` | `{ discard? }` | `{ ok, dir, steps, total }` — closes the final step (settle first), stops recording, finalizes the outputs below, then the server exits. `discard:true` throws the take away and exits. |

- Actions before the first `/step` (page load, login, prep) are recorded but fall **outside
  step 0's window** (dropped by the renderer), matching the scripted pre-step-0 behavior.
  Those `/js` snippets become `config.prep` in the generated `steps.mjs`.
- A `/step` or `/marker` naming a `chapterId` that is not one of `context`, `outcome`,
  `approach`, `risks`, `decision` is recorded as `context` and the response carries a
  `warning`. The session also prints every refused control call to stderr, so a fumbled
  curl can never silently cost the take its narration.
- Login state never enters `steps.mjs`. Any snippet that touches cookies or tokens is
  replaced by a redaction comment in the snapshot; the session's Playwright storage state
  is written to `auth.json` in the workdir instead and named by `config.storageState`.
  `auth.json` is gitignored and is in no share bundle or publish grant. Start a session
  already signed in with `spool live <dir> --auth <storageState.json>` (or `SPOOL_AUTH_STATE`).
- Timeout safety: if no request arrives for **5 minutes**, the session finalizes as if `/end`
  were called (no leaked headless browser).

On `/end` (non-discard) the session dir gets: `video.webm` + `timeline.json` (same contract as
`spool record`), `console.jsonl`, `keyframes/step_NN.png` (one per step, for eyeballing the
take before finishing), and a generated `steps.mjs` snapshot:

```js
// generated by spool live — edit + `spool build` to reproduce this take.
export const config = {
  url: "http://localhost:4747",
  viewport: { width: 1600, height: 900 },
  title: "…",
  storageState: "auth.json",               // present when the session had a login
  prep: async (page, h) => { /* pre-step-0 snippets, credentials redacted */ },
};
export const steps = [
  { name: "…", narration: "…", zoom: "none", run: async (page, h) => { /* the /js snippets that succeeded, in order */ } },
];
```

`spool finish <dir>` runs vo → render → share on that session (no re-record); `spool build`
detects a live/recorded session (video.webm **or capture.mp4** + timeline.json + a
live-generated or absent steps.mjs) and behaves like `finish` instead of re-recording.

## Live control protocol — OS target (spool live --target os → HTTP control server)

`spool live <dir> --target os [--title <t>] [--display <idx>] [--window <name>]` starts a
macOS full-display `ffmpeg avfoundation` capture (real cursor, 30fps CFR H264, long edge
capped at 2560) and serves the same 127.0.0.1 ephemeral-port JSON API. It prints the same
one stdout line (`{"port":N,"session":"<dir>"}`). Recording start is anchored once the output
file is confirmed growing, then a ~1.5s settle precedes step 0 (t=0 is accurate to within a
few hundred ms; freeze-hold retiming forgives the slack). There is **no `page`**, so `/js` is
replaced by `/sh`; the agent drives the desktop out-of-band (osascript/cliclick/its own tools)
between `/step` calls.

| Method + path | Body | Returns |
|---|---|---|
| `POST /step` | `{ name, narration, zoom?, chapterId? }` | `{ ok, index, name, chapterId? }` — closes the previous step (250ms settle + a `screencapture` keyframe) and opens a new one. `narration` required. `zoom` = `"none"` (default) or `{x,y[,scale]}` in capture-pixel coords. |
| `POST /sh` | `{ cmd }` | `{ ok, exitCode, stdout }` — runs `cmd` via `bash -lc`, returns stdout (truncated 4k), and appends `{t, kind:"sh", cmd, exitCode, stdoutHead}` to `console.jsonl`. A convenience logger, not required — the agent may act entirely out-of-band. |
| `GET /status` | — | `{ ok, target:"os", elapsed, completed, current }`. |
| `POST /end` | `{ discard? }` | `{ ok, dir, steps, total }` — closes the final step, SIGINTs ffmpeg and waits for the moov atom to finalize, writes the outputs below, then exits. `discard:true` drops the take. |

5-minute idle timeout finalizes as if `/end` were called. On `/end` (non-discard) the dir gets:
`capture.mp4` + `timeline.json` (contract above, `target:"os"`), `console.jsonl` (the `/sh`
log), `keyframes/step_NN.png` (one per step, live `screencapture` at each step close), and a
**`steps.os.md`** snapshot — a human/agent-readable session record (per-step name + narration
+ the `/sh` commands run). There's no `steps.mjs` (no page driver to reproduce); `spool finish`
sources narration straight from `timeline.json`.

`--window` (single-window capture) is **not implemented** — it falls back to full-display
capture with a stderr notice.

## Plan Spool lifecycle (spool plan → spool share → publish → agent read)

A **Plan Spool** is a watchable proposal and a machine-readable decision packet. The
video explains it; `plan.json` carries the semantics. A workdir holding `plan.json` is
a Plan Spool: `spool share` stamps `kind: "plan"` into `spool.json` and copies the
packet to `share/plan.json`; publish stores it as revision 1 and opens the decision.

```
spool/<slug>/
├── plan.json          # authored by `spool plan init`, checked by `spool plan validate`
├── evidence.json      # optional descriptors (see "Plan Spools" → "evidence.json")
└── share/plan.json    # published copy (written by `spool share`)
```

A workdir holding `reply.json` instead is a **reply spool**: a child recording that
addresses one moment of somebody's plan (see "Replies"). The two files never share a
workdir — a proposal and an answer to one are different spools.

The packet format itself — every field, every rule the validator enforces, the JSON
Schema mirrors and the published copy — is specified once under
[Plan Spools](#plan-spools-planjson-evidencejson-shareplanjson). This section covers
only what happens to a packet after it is valid: the commands, the publish call, the
decision API and the agent read payload.

- **Caps**: 64KB per packet, 24 items per list, 2000 characters per string (300 for `goal`
  and `decision.prompt`).
- **Local finish only for now**: the cloud worker builds and publishes the bundle itself and
  never sees `plan.json`, so `--cloud` on a plan workdir is refused rather than silently
  publishing an ordinary spool.
- **Validation runs three times**: `spool plan validate` while authoring, `spool share`
  before a bundle exists, and the server at publish. An invalid plan is a draft problem,
  so it fails before VO, recording or upload. `spool lint` reports the packet too, so a
  bad plan blocks `spool publish`.

### Commands

```bash
spool plan init <slug> --goal "..." --task <url-or-id>   # writes spool/<slug>/plan.json
spool plan validate <dir> [--json]                        # terse report; exit 1 on errors
spool read <dir|share|watch-url|spool-id> --plan [--json] [--offline] [--transcript]
                                                          # plan + decision status + next allowed action
spool reply <dir|watch-url|spool-id> [--kind …] [--question <id>]  # a child spool that answers a moment
spool status <dir|watch-url|spool-id> --verdict on_plan|changed|blocked  # where the approved work is
```

### Publish (two calls)

Publishing a plan takes two calls. The media goes up first; the plan linkage lands only
after it. The order is the point: a reviewer must never meet a pending decision on a
spool whose video never arrived.

**1. `POST {host}/api/publish`** — a plan spool sends the packet inline as `plan` and the
resolved descriptors as `evidence`, beside the existing `spool` metadata. Both are the
published copies `spool share` wrote (`share/plan.json`, `share/evidence.json`), never
the authored files. The server re-validates them, writes `spools/{id}/src/plan.json` and
`spools/{id}/src/evidence.json`, and returns the upload grants as usual. `kind: "plan"`
without a packet is a 400, so is a packet without the kind, and so is `evidence` without
a packet. The response carries `plan: { pending: true, complete }` — the plan is stored
but not yet open.

**2. `POST {host}/api/publish/{id}/complete`** — the CLI calls this after every upload
grant succeeds. Authorization is the same publish token as the media it completes, and
the spool must belong to the caller (anything else reads as 404). The server then:

- reads the packet back from `spools/{id}/src/*`, never from a second request body, so
  what gets decided on is what the media argues about;
- checks that `l/{id}/final.mp4` is really stored (one retry, for propagation), and
  answers 409 while it is not;
- opens the lifecycle in one statement: `plan_spools` (status + current revision),
  `plan_revisions` (revision 1), `plan_events` (`plan_published`).

The response carries `plan: { revision, revisionId, status }`. The call is **idempotent**:
a retry after a dropped response returns the same revision and the current status, and
writes nothing. Publication analytics fire once, on the call that opened the plan.

The same call links a **reply** spool to its parent by the same rule and for the same
reason (see "Replies"): the descriptor comes back from `spools/{id}/src/reply.json`, the
media must be stored, and until it lands the reply is nowhere on its parent. A spool
that carries neither a packet nor a reply descriptor is a 400.

**`POST {host}/api/publish/{id}/announce`** — the PR comment, and the only call any kind
of spool makes. Same authorization and the same media check as `complete`; it writes
nothing but the comment. The GitHub App leaves the watch-link card on the pull request the
spool's row names, and answers `comment: { posted, action, url }` where `action` is
`created`, `updated`, `unchanged` or `skipped`. `posted: false` carries a `reason`
(`no_installation`, `no_pull_request`, `disabled`), which is the CLI's cue to comment with
`gh` instead — exactly one of the two writes per publish. One comment per spool: the card
carries a `<!-- spool-watch:{id} -->` marker and a re-publish edits it in place. See
[docs/GITHUB-APP.md](./docs/GITHUB-APP.md) §5.

**Between the two calls a plan spool is not watchable.** `/l/{id}`, its embed and its
link preview all answer 404 until the lifecycle row exists, and `GET /api/plans/{id}`
already does. A publish that stops halfway therefore leaves nothing half-published for a
viewer; re-running `spool publish` publishes a whole new id, and the unfinished one
keeps its id (and, on the free plan, its slot) until the owner deletes it from the
dashboard. Access to the published `plan.json` and `evidence.json` matches the media's:
public blobs under the same unguessable id, the same reach as the watch link.

**The free publish cap counts LIVE spools** (`web/lib/publishCap.ts`). A `spools` row is
reserved before it is watchable — the draft lane opens one when a plan is created, and a
cloud render reserves one before the worker has rendered anything — so counting rows
charged a free account for work it abandoned. A row counts once its plan lifecycle has
left `draft`/`recording` AND any platform render that reserved it has reached
`queued`/`running`/`done`; a draft, a render abandoned before `POST
/api/render-jobs/{id}/start`, and a render that errored all cost nothing. Four gates
enforce it and all four embed the same predicate: `/api/publish`, `/api/render-jobs`,
`POST /api/plans` (opening a draft) and `POST /api/plans/{id}/publish` (where the draft
lane pays). Each re-checks under a per-owner `pg_advisory_xact_lock` inside the writing
statement, so concurrent publishes cannot both take the last slot.

**A paid plan is per seat.** `billing.seats` is the subscription quantity (owner
included, minimum 1) and the metered caps in `web/lib/limits.ts` — hosted voice per day,
edit re-renders per month, cloud renders per month — are one seat's allowance multiplied
by it. Published spools stay unlimited on a paid plan, so seats do not scale them.

### The draft lane (`POST /api/plans` → record → publish → request a decision)

Publishing (above) opens a plan whose video **already exists**: the CLI rendered it
locally, uploaded it, and the plan lands on `awaiting_decision` because there is nothing
left to do but decide. An agent that cannot render locally needs the other order — store
the packet first, let the platform do the recording and rendering (SPL-DECISIONS #58).
That is the draft lane, and it is what makes `draft`, `recording` and `published` real
states rather than labels.

```
POST /api/plans                 { plan, evidence?, identity?, title?, format?, policy? }
  → { spoolId, revisionId, revision, status: "draft", links }      plan row + revision 1
POST /api/plans/{id}/sources             { timeline, planScript?, planTheme?, format?, vo?, … }
  → { artifacts, uploads, planReady }                               raw capture goes up
POST /api/plans/{id}/render              { payload? }
  → { jobId, kind, status: "queued" }            opens the take, then renders it
POST /api/plans/{id}/record/start                          draft → recording (optional)
POST /api/plans/{id}/publish                               recording → published
POST /api/plans/{id}/request-decision                      published → awaiting_decision
```

The two lanes meet at `publish` and share everything after it — decisions, questions,
revisions, implementation, proof are one set of rules whichever way the plan was opened.

- **The packet lives in `plan_revisions` from the first call.** There is no blob copy to
  read back, because there is no second request to distrust: the packet was validated and
  stored in one statement. (The publish lane writes `spools/{id}/src/plan.json` precisely
  because its completing call is a *separate* request that must not be trusted with a
  second copy.)
- **The `spools` row is minted in the same statement**, under the same per-owner advisory
  lock and the same free-tier count `/api/publish` takes. Over the cap is a 402. The count
  is of LIVE spools (see below), so the draft this opens does not count itself: opening a
  draft is free, and the slot is charged at `POST /api/plans/{id}/publish`, the edge that
  makes the plan watchable. That gate takes the same lock, so the two lanes cannot both
  spend the last slot.
- **`policy` is the per-plan autonomy override** (`plan_spools.policy`), one of the four
  gate policies. It is the strongest source the merge tap reads (docs/GITHUB-APP.md);
  omit it and the plan inherits the repository's `spool.config.json`. Anything that is
  not one of the four is a 400, so a typo cannot store an override nothing reads.
- **`sources` drives no edge.** Uploading a capture is not the same as starting a take,
  so re-uploading a better one does not walk the state machine twice. Same blob layout,
  content types and 15-minute grant TTL as `/api/publish` — one module writes both
  (`web/lib/planSources.ts`), because the render worker reads exactly one layout.
- **A missing `plan.script.json` is the footgun this lane has.** `src/render/render.mjs`
  turns the plan card layer on only when both `plan.json` and `plan.script.json` are in
  the workdir, and drops it with no error otherwise — the render succeeds and the video
  is quietly an ordinary walkthrough. So `sources` writes `plan.json` itself from the
  stored revision (the packet the video argues is by construction the packet the plan
  holds), writes `evidence.json` beside it, takes the generated script as `planScript`,
  and answers `planReady: false` with a `warning` when it did not get one. `/render`
  repeats the warning. `planTheme` and `format` are merged into `render.json` or a later
  re-render will not match the first.
- **`/render` is the plan lane's door to the worker**, and the reason it exists rather
  than a spool-id field on `/api/render-jobs` is authorization: everything plan-scoped
  goes through `guard()` against one matrix, and a second door with its own owner check
  would be a second answer to "who may act on this plan". `plan.record` gets it right for
  free — owner or agent, and only in `draft`, `recording` or `revised`, so a render
  cannot start against an approved or proved plan. `/api/render-jobs` keeps its own job:
  reserving a FRESH spool for the CLI's `--cloud` finish, where there is no plan row to
  authorize against yet. Both enqueue through `web/lib/renderEnqueue.ts` and both count
  against `caps.cloudPerMonth`, because a cap only one of them counts is not a cap.
  The job kind is decided by what is really stored, not by a flag: `render` when a
  capture is there, `render_packet` when the packet is all there is.
- **A `render_packet` picks its visual layer from the packet, not from a flag either.**
  `inferVisual` in `src/packet/author.mjs` returns `mockup` when the plan's goal or
  outcome names a SURFACE (a screen, a page, a dashboard, a layout, a redesign) AND its
  options are built out of screen parts, and `diagram` otherwise. A design plan is
  decided by looking at the screens, so its beats carry SCREENSHOTS of the product
  (`mockups.json` plus the PNGs it points at, gated by `mocklint.mjs`); every other plan
  carries the diagram DSL (`diagrams.json`, gated by `diaglint.mjs`). The two never mix
  in one video, and a packet may set `plan.visual` to `"mockup"` or `"diagram"` to say
  so outright. `render.json` records which layer was used, so a re-render matches.
- **`/render` opens the take itself when the plan is still in `draft`**, so
  `/record/start` is available but never required. `recording` means A TAKE IS BEING
  PRODUCED — not that a human is at a screen recorder — and on this lane the producer is
  the render worker. For a `render_packet` there is no recorder at all, so demanding
  `/record/start` first would be asking an agent to announce a take it will never make:
  the kind of step that gets skipped, after which the render finishes and the plan
  strands in `draft`, because `publishPlan` only leaves from `recording`. The edge is
  still driven by `startRecording` with its own receipt and its own authorization; this
  only decides when to take it, and a plan already in `recording` or `revised` is left
  alone. The 202 always reports `planStatus: "recording"`, so a client never has to work
  out which of the two opened it.
- **`publish` refuses until the media is really stored**, the one rule publishing has —
  the same check `/api/publish/{id}/complete` makes, for the same reason: a plan that
  became watchable while its video was still uploading would put a reviewer in front of a
  player that 404s, and that cannot be taken back.
- **`request-decision` is the gap the CLI does not have.** A draft-lane plan reaches
  `published` with a working link before anybody is asked, which is where its agent
  invites the people who should decide. A CLI publish *is* the asking, so it skips
  straight to `awaiting_decision` — and calling `request-decision` on a plan already
  there reports `recorded: false` rather than a conflict.

### Decision API

Every route below asks one question, through `authorizePlan` in `web/lib/planAccess.ts`,
which loads the plan's facts and calls `guard()` in `web/lib/planPolicy.ts`. The "Auth"
column names the capability, not a route-local rule. See "Plan access grants" below and
`docs/PLAN-SPOOL-LIFECYCLE.md`.

Every endpoint id in `ENDPOINT_IDS` has a route behind it, and that is a property worth
stating: `nextAction` names an endpoint id, so an id with no route would be the payload
telling an agent to make a call that 404s.

| Method + path | Auth | Returns |
|---|---|---|
| `POST /api/plans` | `plan.create` — any session or `spk_` token | `{ spoolId, revisionId, revision, status: "draft", links }` (see "The draft lane") |
| `GET /api/plans/{spoolId}` | `plan.read` — the watch link's reach | the agent payload below |
| `GET /api/plans/{spoolId}/video` | `plan.read` — the watch link's reach | `{ video, transcript, mediaSpoolId, … }`; `?redirect=1` answers 302 |
| `POST /api/plans/{spoolId}/decisions` | `plan.decide` — signed-in owner or `decider` | `{ ok, status, decision, replayed }`, or 400/401/403/404/409 |
| `GET /api/plans/{spoolId}/events` | `plan.read_events` — owner, agent, `commenter`, `decider` | append-only history of ONE plan |
| `GET /api/events` | ownership — a session or a `spk_` token | the resumable cursor across ALL the caller's plans (see "Agent event stream") |
| `GET /api/plans/{spoolId}/analytics` | `plan.read_analytics` — the owner, nobody else | `{ activity: { counts, milestones, durations, discussion, revisions, access } }` |
| `POST /api/plans/{spoolId}/sources` | `plan.record` — owner or agent, in `draft`/`recording`/`revised` | `{ artifacts, uploads, planReady }` — scoped blob grants (see "The draft lane") |
| `POST /api/plans/{spoolId}/render` | `plan.record` — owner or agent, in `draft`/`recording`/`revised` | `202 { jobId, kind, status: "queued" }` |
| `POST /api/plans/{spoolId}/record/start` | `plan.record` — owner or agent | `draft → recording` |
| `POST /api/plans/{spoolId}/record/discard` | `plan.record` — owner or agent | `recording → draft` |
| `POST /api/plans/{spoolId}/revisions` | `plan.revise` — owner or agent, from `redirected`/`needs_input` | the draft for revision N+1 (see "Revisions") |
| `GET /api/plans/{spoolId}/revisions` | `plan.read` — the watch link's reach | the lineage, with each revision's delta |
| `POST /api/plans/{spoolId}/publish` | `plan.publish` — owner or agent, from `recording` or `revised` | `recording → published`, or `{ ok, revisionId, revision, delta, mediaSpoolId, replayed }` |
| `POST /api/plans/{spoolId}/request-decision` | `plan.request_decision` — owner or agent, from `published` | `published → awaiting_decision` |
| `POST /api/plans/{spoolId}/questions/{questionId}/ack` | `plan.acknowledge` — owner or agent only | `{ ok, questionId, throughMessageId, replayed, blockedBy }` (see "Blocking comments") |
| `POST /api/plans/{spoolId}/implementation/proved` | `plan.mark_proved` — owner or agent, from `implementing` | `implementing → proved`; needs a `summary` |
| `POST /api/plans/{spoolId}/supersede` | `plan.supersede` — owner or agent, from any live state | `* → superseded` |

**Every edge answers the same way.** A transition route returns
`{ ok: true, status, revisionId, revision, recorded }` — `recorded: false` means the call
repeated one that had already taken the edge, which is not an error: an agent that lost a
response must be able to ask again. A refusal carries `reason` (`wrong_state`,
`stale_revision`, `unacked_comments`), `current` (the plan as it now stands) and, on a
block, `blockedBy`.

**Decision body**:

```jsonc
{
  "revisionId": "…",              // required; the revision the reviewer decided on
  "action": "approve",            // one of the nine below
  "optionId": "alternative:queue",// an offered alternative; required for approve_alternative
  "reason": "…",                  // required for the four below, max 2000 chars
  "conditions": ["…"],            // approve_with_conditions only: 1..8, max 2000 chars each
  "expectedStatus": "awaiting_decision", // optional optimistic check
  "idempotencyKey": "…"           // optional; or the Idempotency-Key header
}
```

**The nine verbs** (`DECISION_ACTIONS` in `web/lib/plans.ts`). The set is this size because
the reviewer's answer is not binary, and a plan that can only be approved or redirected
forces every other intent through prose the agent has to guess at. Each one exists because
the AGENT does something different afterwards:

| `action` | from → to | `type` on the receipt | needs |
|---|---|---|---|
| `approve` | `awaiting_decision → approved` | `approve`, or `approved_with_notes` with a reason | the packet to offer `approve` |
| `approve_alternative` | `awaiting_decision → approved` | `select_alternative` | an `optionId` the packet offered |
| `approve_with_conditions` | `awaiting_decision → approved` | `approved_with_conditions` | 1..8 `conditions` |
| `request_changes` | `awaiting_decision → redirected` | `request_changes` | a reason |
| `redirect` | `awaiting_decision → redirected` | `redirect` | a reason |
| `needs_input` | `awaiting_decision → needs_input` | `needs_input` | a reason |
| `park` | `awaiting_decision → parked` | `park` | — |
| `resume` | `parked → awaiting_decision` | `resume` | — |
| `reject` | `awaiting_decision → rejected` | `reject` | a reason |

`request_changes` and `redirect` share an edge and differ in what they ask for: changes
means the approach is right and the details are not, a redirect means the approach is
wrong. `resume` is the only verb that starts anywhere but `awaiting_decision`, which is why
`submitDecision` reads its `from` off `DECISION_EDGES` rather than assuming one.

- **The options are a list, and the list is in the read payload.** A decision is a CHOICE
  between approaches, so `options[]` (see "Agent read payload") resolves the proposed
  approach and every alternative into one shape with a stable `optionId`, and a client
  renders them as one homogeneous set of cards. Tap one, send its `action` and `optionId`.
  Do NOT join `approach`, `alternatives` and `decision.options` by hand: `selectable` is
  the only field that says what this endpoint will accept, and an alternative the packet
  DESCRIBES but did not list in `decision.options` is context, not a choice.
- **The packet bounds what a reviewer may APPROVE, and nothing else.** An approval must
  name an option the plan offered — `approve`, or an `alternative:<id>` it listed — because
  the agent chose the question and an approval is an answer to it. Anything else is a 409
  with `reason: "option_not_offered"`. Every other verb is the reviewer declining the
  question as posed, and **a proposal does not narrow the ways it can be declined**: a
  packet listing only `["approve"]` used to be undeclinable, which made its reviewer a
  rubber stamp.
- **Declining requires a reason.** `request_changes`, `redirect`, `needs_input` and
  `reject` are not actionable without prose, so an empty one is a 400. A rejection is
  terminal, so its reason is the only thing that stops the next proposal being the same one.
- **An approval may carry a caveat.** It stays an approval — R0.2 has no
  `approved_with_notes` state — and the receipt records `type: "approved_with_notes"` so a
  policy gate (R4.3) decides whether it unblocks implementation.
- **An approval may instead carry CONDITIONS, which block.** Each becomes a real steer on
  the plan (`anchor: {"type":"general"}`), written **in the same statement as the
  approval**, so there is no window in which an agent reads `approved` and starts before
  its conditions exist. They block through the existing machinery and nothing new: see
  "Blocking comments". The receipt carries `conditionIds` — ids, not text, by the same rule
  the question events follow, because what was SAID lives in the thread they point at.
- **`parked` is a hold, not a slow approval.** It is a state rather than a bare receipt
  because the agent behaves differently: `awaiting_decision` says keep waiting, `parked`
  says stop. A parked plan takes exactly one verb, `resume`; every other verb answers 409
  with `reason: "wrong_state"`. It can still be discussed, shared and superseded.
- **`rejected` is terminal, and it is not `superseded`.** Superseded means a newer revision
  replaced this one and the link should show the successor; a rejected plan has no
  successor. Nothing moves a rejected plan, `plan.revise` does not reach it, and
  `nextAction` tells its agent to propose a different plan rather than revise this one.
- **The `type` vocabulary** is `DECISION_TYPES` in `web/lib/planEvents.ts`: `approve`,
  `approved_with_notes`, `approved_with_conditions`, `select_alternative`,
  `request_changes`, `redirect`, `needs_input`, `park`, `resume`, `reject`. Additive-only,
  so the five that shipped first keep their meaning. **Read the type, not the status**:
  three verbs land on `approved` and two on `redirected`, so the status alone no longer
  says what the reviewer decided.
- **The write is one statement**, guarded on the current revision and on the state the verb
  starts from, so a decision against a superseded revision writes nothing.
- **Idempotency**: `plan_events.idempotency_key` is unique per plan. Resubmitting a key
  returns the first receipt with `replayed: true` and writes nothing; using it for a
  *different* decision is a 409 with `reason: "key_reused"`. A losing writer waits on the plan
  row's lock, so the winner has committed by the time it reads the receipt back — duplicate
  clicks cannot produce two receipts, or two answers, even when they arrive together.
- **Every conflict is structured.** A 409 carries `reason` — one of `already_decided`,
  `stale_revision`, `unexpected_status`, `option_not_offered`, `key_reused`, `wrong_state`
  (the verb does not apply to this plan's state, so reloading will not help) — plus `current`,
  the plan as it now stands (`{ status, revision, revisionId, decision }`), so a client
  reconciles without a second request.
- **Every decision names a person.** `plan_events.actor_id` holds the deciding Clerk user id
  and `actor_type` the actor the matrix allowed (`owner` or `reviewer`). `GET .../events`
  returns `actor_id` to the owner and their agent only; a commenter reads what happened and
  by which role, never who somebody is.
- **Events are append-only**: database triggers reject `UPDATE` and `DELETE` on `plan_events`.

Lifecycle: `awaiting_decision → approved | redirected | needs_input | parked | rejected`,
and `parked → awaiting_decision`. Deleting a spool cascades its plan rows away.

### Timestamped questions (`plan_questions`, `plan_question_replies`)

A question is about ONE moment of a proposal, so it carries an **anchor** and the
revision it was asked against (roadmap R3.2). Video is how a reviewer finds the moment;
the anchor is how the moment stays addressable after the video is watched.

| Method + path | Auth | Body / returns |
|---|---|---|
| `GET /api/plans/{spoolId}/questions` | `plan.read_questions` — owner, agent, `commenter`, `decider` | `{ spoolId, revisionId, questions: [...] }` |
| `POST /api/plans/{spoolId}/questions` | `plan.ask_question` — same actors, while the plan is discussable | body `{ revisionId, anchor, body }` (`revisionId` optional for a `general` anchor); returns `{ ok, questionId, anchor, at }` |
| `POST /api/plans/{spoolId}/questions/{questionId}/replies` | `plan.ask_question` | body `{ body }`; returns `{ ok, replyId, status, answers, at }` |
| `POST /api/plans/{spoolId}/questions/{questionId}/resolve` | `plan.ask_question`, and the asker or the owner side | `{ ok, questionId, status }` |

**Anchors.** Exactly one of five shapes. The first four are checked against the packet
being asked about, so a question can never point at content that plan does not contain:

```jsonc
{ "type": "chapter",  "chapterId": "approach" }        // a stable chapter id
{ "type": "range",    "start": 12.5, "end": 24 }       // seconds on the final.mp4 clock
{ "type": "evidence", "evidenceId": "ev-schema" }      // a descriptor this revision carries
{ "type": "approach", "approachId": "data" }           // an approach step id
{ "type": "general" }                                  // the plan, not a moment of it
```

A read resolves each anchor to `{ type, chapterId, start, end, label, target, missing }`:
`chapterId` is where the player seeks (an evidence or approach anchor resolves to the
chapter that argued it), and `label` is what was anchored, as it read on the question's
own revision. `#q-{questionId}` on the watch link opens that question and plays its moment.

**`general` is the free-form steer**: a message to the agent about the WORK rather than a
remark about the recording ("stop, staging is mid-migration", "check the batch size
first"). Not everything worth saying to an agent has a timestamp, and before it the only
way to say such a thing was to file it against a chapter it was not really about. Three
ways it differs, each because it points at no content:

- **It needs no `revisionId`.** A steer is not about the content of a revision, so a
  revision landing between reading the plan and sending the message must not lose the
  message; it lands on whatever revision is current. Every anchored question keeps the
  stale-revision 409, because it really is about what was on screen.
- **A revision never obsoletes it.** Redrafting is not an answer to "talk to me before you
  touch billing", and a steer a redraft silently cleared would be a way to dismiss feedback
  by publishing.
- **It resolves to `label: "the plan"`**, `chapterId: null`, `missing: false`. There is
  nothing to seek to, and nothing that can go missing.

It blocks exactly like an anchored steer, through the same one predicate.

**Who wrote it.** `asked_by` / `author_id` hold the publish token's OWNER, so an agent's
message used to read back as its owner's. `author_agent` (migration 0023) holds the token's
own LABEL — one token is one agent install — and surfaces as `author.agent` on every
message. Plans are the addressable unit today (one agent owns one plan), so this is a name
for the thread rather than an address you can route to; an agent registry is future work.

**States**: `open → answered → resolved`, plus `obsolete`.

- **A reply from anybody but the asker answers the question**; a reply from the asker asks
  again. Whether a reply answers is therefore a fact about the thread, not a flag a client
  can forget to set. The comparison is on (id, actor type), so an owner's *agent* answering
  the owner's own question is an answer.
- **Both human and agent replies are the same call and the same record.** `author.type` is
  what tells them apart, so a watch page renders an agent's answer as a response card and
  an agent reads a person's without a second format.
- **Only the asker or the owner side may resolve.** A commenter takes part in the
  discussion; closing somebody else's question would lose the signal that says it is done.
- **A revision obsoletes, never deletes.** Publishing revision N+1 marks every live question
  whose anchored content changed `obsolete`, **in the same statement** as the revision
  (`appendRevision({ obsoleteQuestionIds })`), and stamps `obsoleted_by_revision_id`. Which
  ids those are is `staleQuestionIds` in `web/lib/planQuestions.ts`: a chapter anchor when
  that chapter's slice of the packet changed, an approach or evidence anchor when that item
  changed or is gone, and a range anchor whenever the recording changed — a text-only
  revision passes `recordingChanged: false` and its range anchors survive. One
  `plan_question_obsoleted` event records the batch. `publishRevision` in
  `web/lib/plans.ts` is the only caller: it reads the live questions, asks
  `staleQuestionIds` which of them its packet invalidates, and passes the ids straight
  into `appendRevision`. The receipt returns them as `obsoletedQuestionIds`, so the
  publishing agent learns which threads its revision closed.
- **An obsolete question still shows its original context.** It stores `revision_id`,
  revisions are immutable, so a read resolves its anchor against the packet it was asked
  on. The watch page shows it with its thread and does not offer to seek: the question is
  about a recording the reader is no longer watching.
- **The event log never carries what was said.** `plan_question_created` records the anchor,
  `plan_question_replied` the reply id and whether it answered. The text lives in the
  thread, which is read through `plan.read_questions`.
- **The unlisted link is not a seat at the table.** `plan.read_questions` and
  `plan.ask_question` both exclude `link_viewer`, so a link holder watches the plan and
  never sees the discussion. `plan.ask_question` also excludes `superseded`: a replaced
  revision takes no new questions.

| Table | Grain | Holds |
|---|---|---|
| `plan_questions` | one row per question | `id`, `plan_spool_id` (→ `plan_spools`, cascade), `revision_id`, `anchor_type`, `anchor`, `status`, `body`, `asked_by`, `asker_type`, `author_agent`, `obsoleted_by_revision_id`, timestamps |
| `plan_question_replies` | one row per message | `id`, `question_id` (cascade), `plan_spool_id`, `body`, `author_type`, `author_id`, `author_agent`, `answers`, `created_at` |

Constraints (migrations 0017, 0023): `status` and `anchor_type` are CHECKed against the
vocabularies above; `(status = 'obsolete') = (obsoleted_by_revision_id IS NOT NULL)`, so
obsolescence always names its cause; a composite foreign key
`(plan_spool_id, revision_id) → plan_revisions(plan_spool_id, id)` keeps a question
anchored to a revision of its own plan. Triggers make a question's text and anchor
immutable — only its lifecycle columns move — and replies immutable outright, by the same
rule as `plan_events`.

| Call | Guard | Conflict means |
|---|---|---|
| `createQuestion` | the plan is on the revision being asked about | the plan moved on; reload before asking |
| `appendQuestionReply` | the question is on this plan and not obsolete | no open question with that id |
| `resolveQuestion` | the question is still open or answered | it is already resolved or obsolete |
| `createReply` | the plan is in a state this reply KIND may land in, and the named question is live on it | the plan moved on, or the question is closed (see "Replies") |

### Revisions (roadmap R3.4)

A redirect or an unanswered question sends a plan back to its agent. What comes next is
not an edit: **revision is lineage, not overwrite**. The agent redrafts, publishes
revision N+1, and revision N becomes history the moment the plan's pointer moves off it.

```text
redirected | needs_input
  → POST /revisions   the agent takes revision N as its draft        → revised
  → (edits the packet, re-records if the change is material)
  → POST /publish     revision N+1 lands and supersedes revision N   → awaiting_decision
```

**Two calls, and nothing is written between them.** The draft lives in the agent's
workdir, where it can change as often as it likes; the immutable row appears exactly
once, when the packet and the recording behind it are both final. That is why
`current_revision_id` never points at a draft — a reviewer cannot be shown, or made to
decide on, a revision that is still being written.

**`POST /api/plans/{spoolId}/revisions`** — body `{ parentRevisionId }`. Returns the
clone to start from:

```jsonc
{
  "ok": true, "status": "revised",
  "parentRevisionId": "…", "parentRevision": 1, "nextRevision": 2,
  "plan": { /* revision 1's packet, verbatim */ },
  "feedback": { "action": "redirect", "notes": "…", "at": "…" },  // why it came back
  "mediaSpoolId": "…",   // the recording it keeps unless it publishes a new one
  "opened": true         // false when this call repeated one already open
}
```

**`POST /api/plans/{spoolId}/publish`** — body
`{ parentRevisionId, plan?, evidence?, mediaSpoolId? }`. Writes revision N+1, moves the
plan's pointer, appends `plan_revision_created`, and returns the delta.

- **The delta is structural.** It is computed from the two packets — goal, outcome,
  approach, risks, decision, alternatives, current state, assumptions, evidence, links —
  and never from video frames. `web/lib/planRevision.ts` is the whole of it: pure,
  deterministic, and recomputed on read from two immutable revisions, so a stored delta
  can never drift from the revisions it describes.
- **A material change requires a new recording.** A revision that changes what the video
  argues cannot publish against that video. The material fields are `goal`, `outcome`,
  `approach`, `risks`, `decision`, and any `alternative` the packet offers as a decision
  option. Everything else — current-state facts, assumptions, evidence descriptors,
  links, an unoffered alternative — is a correction, and keeps the parent's recording.
  Refusal is a 409 with `reason: "recording_required"` naming the fields.
- **`mediaSpoolId` names the recording that argues a revision.** `plan_revisions.
  media_spool_id` holds it; revision 1's is the plan's own spool. The plan keeps one
  watch link, and `/l/{spoolId}` plays whichever recording the **active** revision names,
  so a re-recorded revision does not scatter a proposal across several links. A named
  recording must exist, belong to the plan's owner, have its media uploaded, and not
  have opened a plan of its own (`recording_missing`, `recording_in_use`).
- **Where the packet comes from** follows the first publish's rule — what gets decided on
  must be what the media argues about. Naming a `mediaSpoolId` makes the server read the
  packet back from `spools/{mediaSpoolId}/src/plan.json` and ignore the body's; a
  text-only revision uploads nothing, so its corrected packet comes from the body.
- **The write is one statement**, guarded on revision N still being current, so two
  agents redrafting from one parent cannot both land and the lineage cannot fork.
- **Retries replay.** Republishing a packet with no semantic difference from the one
  already published returns that revision with `replayed: true`; a retry carrying
  *different* content is a 409, never a silent overwrite.
- **Every transition is a receipt.** `plan_revision_started` records the parent, the
  state it came from and the decision type that sent it back. `plan_revision_created`
  records `supersededRevisionId`, the revision number, the summary sentence, the changed
  and material fields, the change count, `mediaSpoolId` and `rerecorded`. It carries the
  server's verdict, not a second copy of the plan: the change list is recomputable, but
  whether *this* revision was judged material is a fact only the write knows.

**`GET /api/plans/{spoolId}/revisions`** returns the lineage, oldest first:
`{ activeRevisionId, revisions: [{ revisionId, revision, parentRevisionId, status,
mediaSpoolId, summary, createdAt, delta }] }`. `status` is `active` or `superseded`, and
**exactly one revision is active** — the one `current_revision_id` names. Every other
revision is superseded by construction rather than by a column that could fall out of
step with the pointer.

The watch page shows the delta above the decision buttons, and the agent payload carries
`previousRevisionId`, `changeSummary` and `changes`, so neither a person nor an agent has
to rewatch an earlier spool to learn what moved.

**Publishing a revision also ends the questions it invalidates.** `publishRevision` hands
`staleQuestionIds` the two packets and one fact only it knows — whether the recording
changed (`mediaSpoolId !== inherited`) — and passes the result to `appendRevision`, which
marks those questions in the same statement. The receipt reports them as
`obsoletedQuestionIds` (empty on a replay: the original publish obsoleted them, not the
retry). See "Timestamped questions" for the staleness rule itself.

### Replies (`plan_replies`, `reply.json`, roadmap R4.2)

A plan asks for something. What comes back is not always text: an answer can be worth
recording, a revision has a new take behind it, and a proof IS a video. A **reply** is
a child spool that addresses ONE moment of a parent plan, so an answer lands back where
the question was asked instead of arriving as a second, unrelated link.

```text
spool reply <parent>      →  spool/<slug>/reply.json      the lineage, checked against the parent
spool record | live       →  the take
spool share               →  share/reply.json + spool.json's `reply` block
spool publish             →  media first, then POST /api/publish/{id}/complete
                             which writes plan_replies on the PARENT
```

**Four kinds, each legal only where its question stands.** This is the "validated
against the parent's state" rule, and it is `REPLY_KIND_STATES` in
`web/lib/planReplies.ts` (mirrored in `src/plan/reply.mjs`, because the CLI runs where
no server does; `web/lib/planReplies.test.ts` fails when the two drift).

| Kind | What it says | Parent states |
|---|---|---|
| `answer` | here is the answer to your question | every discussable state |
| `revision` | here is the redrafted proposal | `redirected`, `needs_input`, `revised` |
| `status` | here is where the approved work is (see "Implementation status") | `approved`, `implementing` |
| `proof` | here is the work running | `approved`, `implementing`, `proved` |

`superseded` is absent from every row, by the same rule that stops a replaced revision
taking new questions. `answer` is anybody's to publish; `revision`, `status` and `proof`
are the owner side's — they are statements the proposing side makes about its own plan.

**`reply.json`**, written by `spool reply` and published verbatim as `share/reply.json`:

```jsonc
{
  "version": 1,
  "kind": "reply",
  "replyKind": "answer",                       // answer | revision | status | proof
  "parent": {
    "spoolId": "…",                            // the published plan this answers
    "revisionId": "…",                         // the revision it answers — its ACTIVE one
    "revision": 2,                             // informational
    "watch": "https://…/l/{spoolId}"           // informational
  },
  "anchors": [{ "type": "question", "questionId": "…" }],   // 0–4
  "summary": "It takes a brief lock; here it is against a copy."  // ≤ 300 chars, one line
}
```

**Anchors are the question anchors plus a fifth.** `chapter`, `range`, `evidence` and
`approach` mean exactly what they mean for a question (see "Timestamped questions"), and
`question` names a live question of the parent. A reply carries at most one `question`
anchor: two questions answered by one video is two replies, or one unanchored reply.

**A question anchor resolves THROUGH the question**, to the moment the question itself
was anchored to. That is the whole feature: `opensAt` becomes `…/l/{parent}#q-{id}`,
which the watch page already reads as "show this question and play its moment", so an
answer needs no second deep-link mechanism. A reply with any other anchor opens on its
own timeline row, `…/l/{parent}#r-{replyId}`.

**Parent validation happens twice, and the second time is the one that counts.**
`spool reply` reads `GET /api/plans/{id}` (and `…/questions` when the credential may see
the discussion) and refuses a reply the parent cannot take — so an agent learns before
it records, not after. The publish path re-checks everything against the database,
because a client's copy of a parent can be minutes old:

- **no orphans** — the descriptor must name a parent plan and a revision, and a workdir
  that was never published has nothing to reply to;
- **no cross-plan replies** — the revision must be the parent's ACTIVE one (a stale one
  is a 409 naming the current revision, never a silent re-point), a question anchor must
  be a live question of that plan, and every other anchor must be content that packet
  contains. A composite foreign key `(plan_spool_id, revision_id) → plan_revisions
  (plan_spool_id, id)` makes a row naming another plan's revision unwritable at all.

**The write is one statement.** `createReply` records the reply AND, when the reply is
an `answer` on a question, leaves that answer in the question's thread and moves the
question — in the same statement, for the reason every plan write is one: a video answer
that did not reach the thread would leave a reviewer looking at an open question with
the answer elsewhere on the page. Who answered is decided by the row, exactly as in a
text reply: a reply from anybody but the asker answers the question.

**Publishing a reply is two calls**, like publishing a plan and for the same reason.
`POST /api/publish` takes `reply` inline beside `spool`, checks its SHAPE, and stores it
at `spools/{id}/src/reply.json`; the response carries `reply: { pending: true, complete }`.
`POST /api/publish/{id}/complete` reads the descriptor back from that copy — never from
a second request body — checks the parent, and writes the link. Until it lands the reply
is nowhere on its parent: an answer must never sit on a question thread pointing at a
video that never arrived. The call is **idempotent**: a retry returns the same reply with
`replayed: true` and writes nothing, guarded by the unique index on `reply_spool_id`.

A reply spool is an ordinary spool (`kind: "spool"`, or `"proof"` for a proof reply),
never a plan: a workdir holding both `plan.json` and `reply.json` is refused by the CLI
and by `/api/publish`, because publishing it would open a second lifecycle beside the
parent's. A `revision` reply's recording is named through
`POST /api/plans/{id}/publish`'s `mediaSpoolId` as usual.

| Method + path | Auth | Returns |
|---|---|---|
| `GET /api/plans/{spoolId}/replies` | `plan.read_questions` — owner, agent, `commenter`, `decider` | `{ spoolId, revisionId, replies: [...] }` |
| `POST /api/publish/{id}/complete` | `plan.ask_question` on the PARENT, plus the publish token for the media | `{ id, reply: { replyId, planSpoolId, revision, kind, questionId, answered, opensAt } }` |

Replying is `plan.ask_question` and reading the lineage is `plan.read_questions` — the
same two capabilities the text thread uses, and no third. A reply spool IS a message in
the discussion; it just carries a video instead of a paragraph. The unlisted link
therefore never shows the lineage, and a `spk_` token belonging to anybody but the plan's
owner resolves to `link_viewer`, so in practice every published reply is an agent reply.

| Table | Grain | Holds |
|---|---|---|
| `plan_replies` | one row per reply spool | `id`, `plan_spool_id` (→ `plan_spools`, cascade — the PARENT), `revision_id`, `reply_spool_id` (→ `spools`, cascade, unique — the CHILD), `kind`, `anchors`, `question_id`, `summary`, `status` (the report, on a `status` reply only), `created_by`, `created_at` |

Constraints (migration 0019): `kind` is CHECKed against `REPLY_KINDS`; the composite
foreign key above holds a reply to a revision of its own plan; `reply_spool_id` is
unique, so one recording answers one moment of one plan. A trigger makes a reply
immutable — publish another reply rather than rewriting one — and leaves DELETE to the
two cascades that own it: the plan going, or the reply spool going. The lineage
describes a recording, so it cannot outlive one.

**Both views, on purpose.** The watch page renders the lineage as a **timeline** (every
reply this plan received, in order) and as **compact thread links** (the video answers
inside the question each one answered). Neither is a summary of the other: a reply that
answers no question belongs to no thread, and a thread is about one question rather than
about the proposal. The reply spool's own page carries the third view — a back-link to
the parent moment it addresses, so a reader sent the answer can reach the question.

### Proof linkage (`plan_replies.proof`, roadmap R5.1)

A proof is a reply whose parent is an approved plan, and R4.2 already gave it a lineage:
`replyKind: "proof"` names the plan and the revision it proves, a composite foreign key
makes that link unforgeable, and the bundle's `kind` becomes `"proof"`. What that does
not say is what the proof VERIFIED. Without it a reviewer has to watch the whole
recording and compare it against the proposal in their head, and every deviation lives
in narration — where nobody can find it and no agent can read it.

So a proof **enumerates**, and every deviation is a **field**:

```jsonc
// reply.json / share/reply.json, on a proof and only on a proof
"proof": {
  "mode": "video",                          // video (default) | evidence
  "outcome": { "status": "verified", "note": null },
  "approach": [                             // one entry per approach step of THAT revision
    { "id": "data", "status": "verified", "note": null },
    { "id": "ui",   "status": "partial",  "note": "the mobile layout is not done" }
  ],
  "deviations": [                           // from: outcome | approach (+ id) | plan
    { "from": "approach", "id": "ui", "summary": "The card stacks on narrow screens later." }
  ],
  "override": {                             // absent unless one was asked for
    "unapproved": false, "superseded": true,
    "reason": "The work was built against revision 1."
  }
}
```

- **Three verdicts, one vocabulary**: `verified`, `partial`, `unmet`, used the same way
  for the outcome and for a step. `PROOF_STATUSES` in `src/plan/proof.mjs`, mirrored by
  `web/lib/planProof.ts`; `web/lib/planProof.test.ts` fails when the two drift.
- **Enumeration is complete or it is refused.** Every approach step of the revision the
  proof names needs a verdict, and a step the revision does not have cannot be claimed.
  A missing step would render on the card exactly like one that passed.
- **A verdict that is not `verified` needs a deviation naming it**, and an `outcome`
  that is not `verified` needs a `from: "outcome"` deviation. This is the rule the block
  exists for: a deviation is a field, never a sentence somebody said at 0:48.
- **A proof must verify something.** All-`unmet` is a `status` reply, not a proof.
- **`mode`** says whether the recording or the evidence beside it carries the claim.
  `video` is the default; `evidence` is for low-visibility infrastructure work, and the
  lineage card labels it so a reviewer knows there is no walkthrough to watch.
- **The block belongs to one kind.** A `proof` block on an `answer` is refused by the
  CLI, by `/api/publish`, and by a CHECK constraint (`proof IS NULL OR kind = 'proof'`).

**Two conditions, one explicit escape hatch.** `proofGate` in `web/lib/planProof.ts` is
the only place either is decided, and both refusals name the flag that opens them:

| Condition | Refused because | Opened by |
|---|---|---|
| the plan is not `approved`, `implementing` or `proved` | nobody asked for this work | `override.unapproved` |
| the revision is not the plan's active one | the reviewer is looking at something else now | `override.superseded` |

An override carries a **required reason**, and the reason is rendered on the lineage
card beside the proof: an escape hatch that hid the check it skipped would be worse than
no check. Acknowledging one condition never waves the other through, and no override
reaches a `superseded` plan — an acknowledged proof lands exactly where an `answer`
could, and stops where the discussion stops.

A proof of a superseded revision is judged against **that revision's own packet**, which
is immutable, so a proof of revision 1 enumerates revision 1's steps after revision 2
drops one.

**Publishing a proof can close the plan.** When it proves the ACTIVE revision of a plan
that is `implementing`, the same statement that records the reply takes the
`implementing → proved` edge and writes `proof_published` (funnel step 6) beside
`plan_reply_created`. Only that edge, because it is the only one the transition table
declares; a proof on a plan that never reported starting leaves the status alone. A
proof of a superseded revision closes nothing — it is not about this proposal any more.
The actor check `plan.mark_proved` asks for is already met: `proof` is an owner-side
reply kind.

**The chain, walkable from any node** (`web/lib/planChain.ts`):

```text
plan (plan_spools)  →  decision (plan_decision_submitted)  →  proof (plan_replies.proof)
```

| Method + path | Auth | Returns |
|---|---|---|
| `GET /api/plans/{spoolId}/chain` | `plan.read` — whoever may read the plan | `{ spoolId, plan, decision, proofs, proved }` |

One model serves three entry points, so the card on a plan page and the card on a proof
page cannot tell different stories: `planChain` for the plan, `chainForSpool` for a
child spool that finds its parent first, and `readPlanChain` for the endpoint. All three
render all three nodes, including the empty ones — a proof sitting on a plan nobody
decided is exactly what a reviewer must notice, so the gap is drawn rather than hidden.

The one field narrower than the chain is the decision's **prose**: a redirect reason is
the reviewer talking, so it travels only with `plan.read_questions`. A link holder still
sees THAT the plan was approved and THAT the work was proved.

`planPayload` carries the same three nodes for an agent: `proofs[]` (each with its
one-line `headline` and its deviations) and `links.proof`, the declared field that has
been `null` since the read payload shipped. `spool read --plan` prints them, so an agent
that is about to implement a plan learns somebody already did.

| Column | Holds |
|---|---|
| `plan_replies.proof` | the validated `ProofBlock`, jsonb, null on every other kind (migration 0020) |

### Implementation status (`status` replies, `spool status`, roadmap R5.4)

An approved plan says what will happen. A **status spool** says what did: a `kind:
"status"` reply carrying a report a reviewer reads in seconds, and a recording that
shows it. It is a reply and nothing more, so it inherits the plan's permissions exactly
— no new table, no new capability, no second lifecycle.

```text
spool status <parent> --verdict …  →  spool/<slug>/reply.json + steps.mjs   the report + the narration skeleton
spool live | record                →  the take
spool share → spool publish        →  the report lands on the parent, verdict first
```

**The report**, inside `reply.json` beside the fields every reply has:

```jsonc
{
  "version": 1, "kind": "reply", "replyKind": "status",
  "parent": { "spoolId": "…", "revisionId": "…", "revision": 2, "watch": "https://…" },
  "anchors": [{ "type": "approach", "approachId": "data" }],   // 0–4, as any reply
  "summary": "on plan · the approved plan still holds",        // defaults to the headline
  "status": {
    "verdict": "on_plan",              // on_plan | changed | blocked — the headline
    "planValid": true,                 // does the approved plan still hold?
    "reason": "milestone",             // milestone | blocker | decision — the cadence
    "completed": ["data"],             // approach step ids finished, ≤ 20
    "changed": null,                   // what departs from the approved plan, ≤ 400 chars
    "blocked": null,                   // what stops the work, ≤ 400 chars
    "next": "Render the verdict."      // what happens next, ≤ 400 chars
  }
}
```

The four things R5.4 asks a status to state map one to one: **completed** is
`completed`, **changed** is `changed`, **blocked** is `blocked`, and **whether the
approved plan remains valid** is `planValid`. `verdict` is the skimmable headline over
all four — the acceptance criterion is that a reviewer tells on-plan from changed from
blocked without watching anything.

There is no `done` verdict. Work that finished is `on_plan` with every approach step in
`completed`, and the recording that shows it running is a `proof` reply.

**A report may not contradict itself.** These rules run in the CLI before a take is
recorded (`checkStatusReport` in `src/plan/status.mjs`) and again on the server at
publish (`validateStatusReport` in `web/lib/planStatus.ts`; `web/lib/planStatus.test.ts`
runs both over one table and fails when they disagree):

- `on_plan` with `planValid: false` is refused — the verdict for a plan that no longer
  holds is `changed`;
- `changed`, or any report with `planValid: false`, must say what changed;
- `blocked` must say what blocks it, and its cadence is `blocker` or `decision`, never
  `milestone`;
- a `milestone` must name at least one completed approach step — a milestone that
  finished nothing is the per-commit noise this feature refuses;
- every `completed` id must be an approach step OF THIS PLAN, checked against the packet
  by whoever holds it (offline, an unknown approach is not an empty one: the server
  checks again);
- a `blocked` report with no `next` is a warning, not a refusal.

**Explicit action only.** A status is recorded by an agent that decided to record one.
`spool status` refuses to run inside a git hook (`GIT_INDEX_FILE`, or `GIT_AUTHOR_DATE`
with `GIT_DIR`), and the `reason` vocabulary is the cadence rule made a field: a status
is worth a video at a material **milestone**, at a **blocker**, or when the work needs a
new **decision**. `spool reply --kind status` is refused and points here, so a
verdict-less progress video cannot be recorded at all.

**One command, one template.** `spool status` reads the parent exactly as `spool reply`
does (identity, active revision, state, anchorable ids), refuses a status the plan
cannot take — it needs `approved` or `implementing` — and then scaffolds two files: the
descriptor, and a `steps.mjs` whose narration is ordered verdict → done → changed or
blocked → next (`src/plan/status-template.mjs`). It never overwrites a `steps.mjs` an
agent already authored unless `--force` says so.

**Where it appears.**

| Surface | Shows |
|---|---|
| the plan watch page | the NEWEST status, under the decision it reports on: verdict chip, one line per fact, a link to the recording |
| the lineage timeline | every status in order, each row leading with its verdict |
| a status spool's own page | the same verdict above its video, plus the back-link to the plan |
| `GET /api/plans/{spoolId}` | `implementation`: the newest status, or null (see "Agent read payload") |
| `spool read --plan` | a `work:` block above the plan content — an agent picking work up mid-flight asks this before it reads an approach step |

Only the newest status is shown as the answer to "where is this work?": the rest are
history, and the timeline already reads them in order. **No status is not "on plan"** —
`implementation` is `null`, and nothing renders it as a verdict.

**Persistence** is one nullable `jsonb` column, `plan_replies.status`, with a CHECK that
no other kind carries one (migration 0020). That a `status` reply always carries a
report is enforced where the descriptor is validated, for the same reason
`REPLY_KIND_STATES` is not a constraint: it is a product rule, and a row written before
the column existed is history rather than a violation to fail a deploy on.

**Permissions are the reply's own**, with no exception: publishing is
`plan.ask_question` on the parent and owner-side (a status is a statement the proposing
side makes about its own plan), and reading is `plan.read_questions` — so the unlisted
link never shows a status, and `implementation` is null for a reader who cannot see the
lineage.

### Plan access grants (`plan_grants`, invite tokens)

Sharing a plan is one row per person (roadmap R2.5). A row names one audience and one
**level** — `viewer`, `commenter`, `decider`, `owner` — and the level maps to the actor
the permission matrix reasons about (`LEVEL_ACTOR`). Possession of the unlisted link is
`viewer` and nothing more, so decision rights are never inferred from a link.

| Method + path | Auth | Body / returns |
|---|---|---|
| `GET /api/plans/{spoolId}/access` | `plan.read_access` — owner or their agent | `{ spoolId, access: [{ id, level, email, userId, status, expiresAt, createdAt }] }` |
| `POST /api/plans/{spoolId}/access` | `plan.grant_access` + the level must be grantable | body `{ level, email }` or `{ level, userId }`, plus `ttlDays?`; returns `{ grantId, level, token, expiresAt }` |
| `DELETE /api/plans/{spoolId}/access/{grantId}` | `plan.revoke_access` — owner or their agent, in every state | `{ ok, grantId, level }` |
| `POST /api/plan-invites/accept` | the token itself, plus a Clerk session | body `{ token }`; returns `{ ok, spoolId, level }` |

- **`token` is returned once.** Only its SHA-256 is stored (`token_hash`), so it can
  never be read back or re-sent. It is `pinv_` + 32 random bytes, base64url. A direct
  grant by `userId` has no token and is live at once; `token` is then `null`.
- **An invite is single-audience and single-use.** It carries one plan, one address and
  one level. Redemption requires a signed-in user whose **verified** address matches, and
  binds the grant to them; a second person presenting the same token is refused.
- **Every invite expires**: 14 days by default, 1 to 30 by `ttlDays`. A CHECK constraint
  makes a token without an expiry unwritable. `expires_at` bounds the *token*; once
  redeemed the grant lives until it is revoked.
- **Revocation is one `UPDATE`** (`revoked_at`), allowed in every state. A revoked grant
  leaves the facts a route loads, so the next request from that person is a link viewer.
- **Redemption failures are all 404**, so a caller cannot tell an unknown token from an
  expired, revoked, taken or misaddressed one.
- **`plan_access_granted` / `plan_access_accepted` / `plan_access_revoked`** land in
  `plan_events`, in the same statement as the change. Their payloads carry `grantId` and
  `level` only: the event log is readable by every commenter, the access list is not.

| Table | Grain | Holds |
|---|---|---|
| `plan_grants` | one row per share | `id`, `plan_spool_id` (→ `plan_spools`, cascade), `level`, `email`, `user_id`, `token_hash`, `expires_at`, `accepted_at`, `revoked_at`, `created_by`, `created_at` |

Constraints (migration 0015) carry the rules the code cannot be trusted to keep alone:
`level` is a CHECK against the `GRANT_LEVELS` vocabulary; a row names an address or a
user; a token always has an expiry; an accepted grant always names a user. Partial unique
indexes stop a second live grant for one person, a second open invite for one address,
and a repeated token hash.

Writes go through `web/lib/planStore.ts` like every other plan table:

| Call | Guard | Conflict means |
|---|---|---|
| `createGrant` | no live grant for that person or open invite for that address | already shared with them |
| `acceptGrant` | unrevoked, unlapsed, addressed to this user, unclaimed by another | the token is not valid for this requester |
| `revokeGrant` | the grant is on this plan and still live | no live grant with that id |

### Plan persistence (`plan_spools`, `plan_revisions`, `plan_events`)

`spools` stays the universal published-media record. The three tables below carry the
mutable lifecycle beside it, so a decision never rewrites the watch artifact. `edit_jobs`
is untouched: it models render operations, not product decisions.

| Table | Grain | Holds |
|---|---|---|
| `plan_spools` | one row per plan | `spool_id` (PK → `spools.id`), `owner_id`, `status`, project identity (`repo_owner`, `repo_name`, `project_id`), `current_revision_id`, `policy`, timestamps |
| `plan_revisions` | one row per revision | `id`, `plan_spool_id`, `parent_revision_id`, `number`, `plan`, `evidence`, `summary`, `media_spool_id`, `created_by`, `created_at` |
| `plan_events` | one row per thing that happened | `id`, `plan_spool_id`, `revision_id`, `type`, `actor_type`, `actor_id`, `payload`, `idempotency_key`, `created_at` |
| `plan_grants` | one row per share | see "Plan access grants" above |
| `plan_questions` / `plan_question_replies` | one row per question / per message | see "Timestamped questions" above |
| `plan_replies` | one row per reply spool | see "Replies" above |

- **Project identity is the repository first.** `repo_owner`/`repo_name` come from the
  PR link at publish, the same source `spools` uses. `project_id` is the optional second
  identity for a workspace that is not one GitHub repository. All three are nullable.
- **`status` is the lifecycle state** from `docs/PLAN-SPOOL-LIFECYCLE.md`. A CHECK
  constraint holds the column to that vocabulary; the legal edges live in
  `web/lib/planPolicy.ts` and `web/lib/planStore.ts` refuses an edge that is not listed.
- **`current_revision_id` is a revision of the same plan**, enforced by a deferrable
  composite foreign key `(spool_id, current_revision_id) → plan_revisions(plan_spool_id, id)`.
  It is deferrable because a plan and its first revision are written by one statement.
- **Revisions are immutable.** A database trigger rejects every `UPDATE` on
  `plan_revisions`, approved or not, and rejects `DELETE` while the plan still exists.
  A material change publishes revision N+1 with `parent_revision_id` set. Deleting the
  spool still cascades the whole plan away.
- **`media_spool_id` is the recording that argues one revision** (migration 0017). It
  carries no foreign key, and was not backfilled, for the same reason: an immutable row
  can be neither updated nor deleted while its plan lives, so no `ON DELETE` action could
  ever fire and no backfill could ever run. `NULL` means the plan's own spool, which is
  what every row written before that migration is; existence and ownership of a named
  recording are checked at write time instead.
- **Events are append-only.** Triggers reject `UPDATE` and `DELETE` on `plan_events` by
  the same rule.

Every write goes through `web/lib/planStore.ts`, the one module that sends plan SQL:

| Call | Guard | Conflict means |
|---|---|---|
| `createPlan` | `ON CONFLICT (spool_id) DO NOTHING` | the plan already exists; nothing was forked |
| `appendRevision` | `current_revision_id = parent AND status = from` | someone else published revision N+1 first |
| `transition` | `status = from` (and optionally the current revision) | the plan already moved on |
| `appendEvent` | the plan exists, and the revision belongs to it | no such plan or revision |

`transition` and `appendEvent` also take an optional `idempotencyKey`. A repeated key
inserts nothing and reports `exists`, so the caller reads the first receipt back instead
of writing a second one; `eventByIdempotencyKey` is that read.

Each of those is **one statement**: the production driver is Neon over HTTP, which
offers no interactive transaction, so the state change and the event that records it
travel together and commit together. Concurrency is handled by compare-and-swap rather
than by a read-then-write, so two agents publishing from the same parent revision cannot
both win — the loser writes nothing and reports `conflict`.

Read paths are index-backed: `(owner_id, status)`, `(repo_owner, repo_name, status,
updated_at)`, `(status, updated_at)`, `(project_id, status, updated_at)` for lists;
`(plan_spool_id, number)` for lineage; `(plan_spool_id, created_at, id)` and
`(plan_spool_id, revision_id, type, created_at)` for history; and the partial unique
`(plan_spool_id, idempotency_key)` for a replay. `web/tests/planStore.dbtest.ts`
asserts the plan of each read against a loaded table, so an index change that breaks a
read path fails the suite.

### Agent read payload (`spool read --plan --json`, `GET /api/plans/{spoolId}`)

```jsonc
{
  // Bumped only for a breaking change. The payload is ADDITIVE-STABLE: fields are added
  // and never removed or repurposed, so an agent reads what it knows and ignores the rest.
  "payloadVersion": 1,
  "spoolId": "…", "kind": "plan", "revision": 1, "revisionId": "…",
  "status": "approved",                                    // draft when unpublished, unknown when the host is unreachable
  // `action` is the verb the reviewer took; `type` is what it means, and `options[]`
  // below says which option won. READ THEM, not just `status`: three verbs land on `approved` and two on `redirected`, so the status alone
  // cannot say whether to build the headline approach, build a named alternative, or
  // honour a list of conditions. `conditionIds` names the steers an approval attached —
  // ids, because what was SAID lives in the thread they point at, and `blockedBy` is where
  // an agent meets the words and the only place it can act on them.
```

**One call is the contract.** `status` alone does not say whether the reader may start
work, so `nextAction` says it outright and `may` carries the rest. Both are computed for
the resolved `actor`: an agent is never told to decide (it holds no `plan.decide`, in any
state), and a reviewer is never told to implement.

`nextAction.action` is a closed, additive vocabulary (`NEXT_ACTIONS` in
`web/lib/planNextAction.ts`): `submit_decision`, `start_implementation`,
`answer_questions`, `revise`, `publish_revision`, `request_decision`, `mark_proved`,
`record`, `acknowledge_comments`, `await_decision`, `await_revision`, `publish_plan`
(CLI-only, for a packet no host has yet), `none`. Deciding and implementing rank above
answering questions, because an approved plan is already unblocked; in every state where
the reader can do neither, unanswered questions are the gate and win. An unacknowledged
steer outranks all of them — see below.

### Blocking comments (`plan_comment_acked`, SPL-DECISIONS #58)

> comment = steer, decide = approve/redirect, merge = PR — all immutable events the agent
> reads back. **A comment blocks: an agent may not proceed past an unacknowledged one.**

A **steer** is a live thread (`open` or `answered`) on the plan's CURRENT revision, OPENED
by somebody other than the agent — the owner, a `decider` or a `commenter`. It blocks until
the agent acknowledges it. A thread the AGENT opened never blocks the agent, replies and
all: an answer it asked for is not a steer aimed at it, and blocking there would make
asking a question a penalty for asking.

**Acknowledging is not answering.** The ack records that the agent READ the steer; the
question stays `open` and a reply to `../replies` is what actually resolves it. The split
is the point: the rule stops an agent running past feedback, and it must not become a way
for the agent to declare the feedback handled.

**An ack covers MESSAGES, not threads.** A steer is a conversation — owner steers, agent
acks and replies, owner says "no, the other one" — and an ack keyed to the question would
let that third message through unacknowledged forever, because the thread was acked in its
first minute. So an ack names the message it read THROUGH (the newest in the thread when it
ran), and every steering message written after it blocks again. One ack still settles a
backlog: reading the newest message means having read the thread.

```
POST /api/plans/{spoolId}/questions/{questionId}/ack     { "note": "switching to the queue" }
→ { "ok": true, "questionId": "…", "revisionId": "…", "throughMessageId": "…",
    "replayed": false, "blockedBy": [ … ] }
```

- **Only the side that would proceed may ack.** `plan.acknowledge` names the owner and
  their agent and nobody else. A reviewer clearing the block they raised is the one thing
  the rule exists to prevent, and it answers 403.
- **The ack is a receipt**, appended to `plan_events` like every other fact, with the retry
  key `ack:{questionId}:{throughMessageId}` — or the bare `ack:{questionId}` when the
  newest message IS the opening question, so an ack recorded before this rule and one
  recorded after are the same receipt rather than two. The key is unique per plan, so
  acking the same state of a thread twice writes nothing and reports `replayed: true`,
  while acking after a follow-up correctly writes a new one.
- **Resolution outranks acknowledgement.** A question the asker closed, or a revision made
  obsolete, is not a blocker — acked or not, follow-ups and all.
- **`blockedBy` names what is left**, in the ack's own response and in the agent read
  payload, so an agent never has to guess whether it is clear. Each entry carries `unacked`
  (every steering message since the last ack, oldest first) and `latest`, so an agent shown
  a thread reads the correction and not only the instruction it reversed.
- **An `approve_with_conditions` blocks through this and nothing else.** Its conditions are
  ordinary `general` steers written in the same statement as the approval (see "Decision
  API"), so an approved plan can be blocked out of `start_implementation` with no second
  mechanism to keep in step with this one.

What a block withholds, and what it deliberately does not:

| Withheld while a steer is unacked | Never withheld |
|---|---|
| `start_implementation`, `mark_proved`, `request_decision`, `publish_revision`, `revise`, `record` | `submit_decision` — the reviewer's own call; a comment must not stop a human deciding |
| | `answer_questions` — blocking it would deadlock the plan |
| | `recordImplementationBypass` — refusing it only moves "somebody built this anyway" out of the log |

**The payload and the routes say the same thing.** `nextAction` becomes
`acknowledge_comments` and `blockedBy` fills in; the write paths independently answer 409
with `reason: "unacked_comments"` and the same list. One module decides both
(`web/lib/planBlocking.ts`), because a payload that says "you may start" beside a route
that refuses would be worse than no rule at all.

### Agent event stream (`GET /api/events`)

One resumable cursor over `plan_events`, across every plan the caller owns. This is the
agent's side of the loop: one call answers "what has happened since I last looked?" and
hands back the place to resume from.

**It is a cursor, not a second event system.** `plan_events` is the append-only record
every plan write already lands a receipt in — a publish, a decision, a question, a reply,
a grant, a revision, an ack. This endpoint reads it in order. Nothing is written here and
no event type is invented here, so the stream cannot disagree with the plans it describes.

```
GET /api/events?cursor=…&planId=…&limit=100&wait=25&tail=1
Authorization: Bearer spk_…

{
  "payloadVersion": 1,
  "events": [
    {
      "id": "…",                            // plan_events.id
      "type": "plan_decision_submitted",    // OPEN vocabulary — branch on what you know
      "planSpoolId": "…",
      "revisionId": "…",                    // null for an event about the plan itself
      "actor": { "kind": "reviewer", "id": "user_…" },
      "payload": { "action": "approve", "type": "approve", "optionId": null, "reason": null, "conditionIds": null },
      "at": "2026-08-20T11:22:33.123Z",
      "cursor": "MjAyNi0wOC0yMFQxMToyMjozMy4xMjM0NTZafDNmMjUwNGUw…"
    }
  ],
  "cursor": "…",        // where to resume; unchanged from the request when the page is empty
  "hasMore": true,      // the page filled — call again at once instead of waiting
  "waited": false
}
```

**Scope is ownership.** A `spk_` token streams the plans its owner holds; a signed-in
person streams their own. The owner is resolved from the credential and there is no
parameter that could widen it. Somebody invited to comment on one plan reads that plan's
history at `GET /api/plans/{id}/events` — a firehose across every plan a person was ever
invited to is a different product with a different privacy question, and this endpoint
does not answer it. No credential at all is a 401.

**Cursor semantics.** The cursor is an opaque, URL-safe token. Its shape is not the
contract: do not parse it, store it and send it back.

- **Resume is exact.** The read is `(created_at, id) > cursor`, strictly. `plan_events`
  is append-only — migrations 0013 and 0014 reject `UPDATE` and `DELETE` — so the pair is
  a stable total order and a cursor into it is never invalidated. Every event is returned
  **exactly once**: no gaps, no repeats.
- **The id is in the cursor because timestamps tie.** Two events written by one statement
  (a revision and the questions it obsoleted, say) share a `created_at` to the
  microsecond. Their order relative to each other is arbitrary — they are simultaneous
  and the stream does not claim an order it cannot know — but each is delivered once, and
  resuming from a page boundary INSIDE such a group is exact.
- **Microseconds are preserved.** `created_at` is a `timestamptz`; a JavaScript `Date`
  holds milliseconds. The cursor carries the exact text Postgres emitted, so it never
  rounds and never skips or replays an event 456µs from its neighbour.
- **A cursor this server did not write is a 400**, not "start from the beginning":
  silently replaying the whole history would look like a working resume.

**Replay guarantees.** No `cursor` means from the very beginning, so an agent that lost
its cursor recovers everything rather than silently missing what it was away for. `tail=1`
is the opt-in for the other case — it returns zero events and a cursor anchored at the
newest one, so a fresh agent can start following without being handed the history first.
`tail` is ignored when a `cursor` is given.

**Long polling.** `wait=<seconds>`, 0 to 25, holds the request open while there is
nothing new: the handler polls once a second and returns the moment an event lands. It
always answers — an empty `events` with an unchanged `cursor` is a valid answer, and the
caller simply asks again. It is a loop rather than a subscription because the function
holding it is a serverless invocation with a wall clock; the ceiling leaves headroom
inside that budget so a wait ends as a wait and never as a timeout. `x-spool-max-limit`
and `x-spool-max-wait` state the bounds on every response.

**`limit`** is 1..500, default 100. `hasMore` is true when the page filled, which means
call again immediately rather than waiting.

### Reading it (`spool read <target> --plan`)

| Target | Read |
|---|---|
| workdir (`plan.json` + `share/`) | live status from the host in `share/published.json`, else the local packet |
| `share/` bundle on its own | the same, from the bundle's own directory |
| watch URL (`https://host/l/{id}`) | the host named by the URL |
| bare spool id | the configured host |

- **Auth.** The publish token goes out as `Authorization: Bearer …`. Without it the host
  answers as it would to a link holder — the plan, but no open questions — so an agent
  reading its own plan would silently miss the work blocking it. The token is sent ONLY to
  the configured host, or to one named on purpose with `--host`/`--token`: a watch URL and
  a travelling bundle both carry an origin the reader did not choose, and a pasted link
  must not be able to collect the credential.
- **Offline.** `--offline` answers from the bundle alone: no network, no credentials. The
  status is never invented — an unpublished packet is `draft`, and a bundle whose plan was
  published reads `unknown` with an `error` note. Both carry a `nextAction` that refuses
  implementation, which is the one mistake this command must not enable. The same fallback
  runs unasked when the host is unreachable or answers 404.
- **Narration.** The default read is a digest plus references: an agent already holds the
  plan in structured form, so the words cost context and add nothing. `--transcript`
  returns them, adding a `transcript` field to `--json` and a `transcript:` block to the
  digest. The hosted transcript is a public blob and is fetched unauthenticated.
- **Digest.** The human default leads with `plan: <status>` and `next: <action>`, then the
  goal, outcome, approach, risks, evidence (label and ref only, never an excerpt), open
  questions with where to reply, and the links.

### Implementation gate (`spool gate`, `spool.config.json`)

A Plan Spool is a proposal until something acts on the decision. The **implementation
gate** is that something: one check that answers "may this work start?" from the
project's policy and the plan's status (roadmap R4.3).

The gate runs in the CLI and, for a pull request, as a GitHub commit status. It does
not try to enforce anything inside an agent runtime. Two surfaces, both auditable, are
worth more than a promise nobody can keep.

**Policies**, weakest first:

| Policy | What it does |
|---|---|
| `off` | Plan Spools are informational. The gate allows everything and makes no network call. |
| `advisory` | The gate warns when work starts without an approved plan. It never blocks. |
| `required` | An approved active plan is required before implementation. |
| `high_risk_required` | Required for high-risk work only. Everything else is advisory. |

**Resolution.** With nothing configured, a project is `advisory`. Four sources may
configure it, and **the strongest configured source wins**:

| Source | Where |
|---|---|
| `flag` | `--policy` on any `spool gate` command |
| `env` | `SPOOL_PLAN_POLICY` |
| `repo` | `policy` in `spool.config.json` |
| `prefs` | `planPolicy` in `~/.spool.json` |

A flag and the environment can therefore RAISE the policy, never lower it. A gate a
local flag can switch off is not a gate; `--bypass --reason` is the one way past a
policy, and it is recorded. `spool gate policy [--json]` prints the resolved policy,
every source that set it, and the high-risk definition — the whole input to a verdict,
so anyone can reproduce it.

**`spool.config.json`** sits at the repository root. The gate reads the nearest one at
or above the working directory, and never looks above the repository root:

```jsonc
{
  "policy": "advisory",                    // off | advisory | high_risk_required | required
  "plan": "spool/add-questions",           // optional: the active plan (workdir, watch URL or spool id)
  "highRisk": {                            // optional: what `high_risk_required` covers
    "paths": ["web/db/migrations/**"],     // globs; ** crosses directories, * does not
    "labels": ["security"],                // pull-request or task labels, case-insensitive
    "categories": ["migration"]            // task categories, case-insensitive
  }
}
```

With no `highRisk` block, a built-in default applies: migrations, `*.sql`, `auth`,
`billing`, `payments`, `secrets`, `.env*`, `.github/workflows`, `Dockerfile`, `infra`
and `terraform`. `DEFAULT_HIGH_RISK_PATHS` in `src/gate/policy.mjs` is the list.

**Which files the work touches**, best source first: `--paths`, then the pull request's
changed files (`--pr`), then this checkout's working tree. An empty result is not
evidence that the work is safe, so under `high_risk_required` it counts as high risk.
An agent that has not written the code yet declares its files with `--paths`.

**The verdict.**

| Plan status | `off` | `advisory` | `high_risk_required` | `required` |
|---|---|---|---|---|
| `approved` or `implementing` | allow | allow | allow | allow |
| anything else | allow | warn | block if high risk, else warn | block |

An approval carrying a caveat is `approved_with_notes` — a decision type, not a state
(see "Decision API"). It **unblocks** the work, and the caveat travels with the verdict
for the agent to honour. A plan the gate cannot read fails closed: an unreachable host,
a missing plan, and several plan workdirs with none named all read as "not approved".

Each verdict carries reason codes a caller can branch on: `policy_off`,
`plan_approved`, `plan_approved_with_notes`, `plan_implementing`, `plan_not_approved`,
`plan_status_unknown`, `plan_missing`, `plan_ambiguous`, `high_risk`, `not_high_risk`,
`bypassed`.

**Commands.** Exit codes are the contract: 0 may proceed, 1 blocked, 2 the check could
not run.

```bash
spool gate policy [--json]                  # what is in force here, and why
spool gate check [--command "npm run migrate"] [--paths a b] [--pr] [--json]
spool gate run -- npm run migrate           # check, then run it (blocked: it never runs)
spool gate status --pr [number]             # publish the verdict as a commit status
```

A blocked run prints, on stderr, the command it stopped, the policy and its source, the
plan and its status, the reason, the watch link to get a decision, and the exact
`--bypass` command to proceed anyway.

**Every run without an approval is recorded** — under every policy, including
`advisory`. Two places:

- `<repo>/.spool/audit.jsonl`, append-only, one JSON object per line. It works offline
  and with no account. It records the command and how many paths were involved, never
  the paths themselves and never file contents.
- The plan itself, best-effort, at the host the watch link names:
  `POST /api/plans/{spoolId}/implementation/start` for approved work (`approved` →
  `implementing`), and `POST /api/plans/{spoolId}/implementation/bypass` for work that
  started anyway (no state change). A network failure never decides whether an
  implementation may proceed.

Both server calls take `{ revisionId?, policy, reason?, highRisk?, idempotencyKey? }`,
are authorized by `plan.start_implementation` and `plan.record_bypass`, and are
idempotent by key. A bypass must say why. The stored event carries the policy, the
bypass flag, the risk flag, the status it started from and the reason — never the
command, and never a path. Both emit the `implementation_started` analytics event with
`policy`, `planStatus` and `bypassed` (docs/PLAN-SPOOLS-ANALYTICS.md).

**Pull requests.** `spool gate status --pr` posts a commit status with context
`spool/plan-gate` to the PR's head commit through `gh`. `failure` when blocked, else
`success`; the description is the one-line verdict and the target URL is the watch
link. Protect a branch with that context to make `required` mean required.

```yaml
# .github/workflows/plan-gate.yml — on pull_request
- uses: actions/checkout@v4                 # the policy lives in spool.config.json
- uses: aaarnv/spool@v1
  with: { install-chromium: "false" }
- run: spool gate status --pr ${{ github.event.pull_request.number }}
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}   # `gh` posts the status with this
```

The step exits 1 when the gate blocks, so the job fails as well as the status. The
gate reads the PR's labels and changed files, so the high-risk definition works from a
pull request without a checkout of the branch's working tree.

### GitHub integration (`spool plan pr`, `spool plan stale`, roadmap R5.2)

A plan and the pull request that implements it are two halves of one review. This
section is how they find each other: a reviewer opens the pull request and finds the
plan, and an agent asks whether the plan is still about this code before it acts on it.

Everything here is an **extra surface**. GitHub never holds a plan, never decides one,
and no failure of these commands can fail a publish, a build, or a pipeline.

**Links.** `links.pr` and `links.issue` are the two links a tool acts on. Both accept
four written forms:

| Form | Example |
|---|---|
| pull-request URL | `https://github.com/acme/coach/pull/57` |
| issue URL | `https://github.com/acme/coach/issues/12` |
| short form | `acme/coach#57` |
| number, resolved against `links.repo` | `57` or `#57` |

A GitHub URL of the **other** kind is an error (`wrong-github-kind`): a `links.pr` that
is an issue sends every tool that follows it to the wrong place. Anything spool does
not recognise — a GitLab merge request, a Jira key — is a **warning**
(`unrecognized-github-ref`), and the packet stays valid: a project may track work where
spool has no integration. `links.task` is unconstrained, but when it happens to be a
GitHub issue the PR comment links it. The portable JSON Schema mirror carries the
wrong-kind rule; the short forms need `links.repo`, which a schema cannot read, so they
are validated by the CLI only.

`links.branch` and `links.commit` are the plan's **source revision** — the code the
proposal was written against. `spool plan init` reads them from the checkout, and the
staleness check below is what they are for.

**Opting in.** The `github` block of `spool.config.json`:

```jsonc
{
  "github": {
    "comment": false,                  // post/refresh the plan comment on the PR (default false)
    "stale": { "commits": 10, "days": 14 }   // how far the source revision may drift
  }
}
```

Commenting is **off until a repository turns it on**. A tool that starts writing on
pull requests the moment somebody installs it is a tool teams uninstall. Each `stale`
value may be `null` to switch that check off.

**The comment.** `spool plan pr [dir]` renders one compact comment and puts it on the
pull request: the plan's status, its goal, the decision it asks for (or the decision it
received), the source revision, the open-question count, the staleness verdict, and the
watch link. The comment is anchored by a hidden marker, `<!-- spool-plan:<key> -->`:

- **one comment per plan.** A run finds its own comment by marker and rewrites it in
  place. An identical body is not written at all, so nobody is notified twice.
- **the key survives publishing.** Before publishing, the key is the workdir slug;
  after, it is the spool id. A run looks for both and re-keys the comment it finds, so
  a plan that commented as a draft does not post a second comment once published.
- **the pull request is recorded once.** The first run writes the resolved pull request
  into `links.pr`, so the plan knows its pull request
  wherever it travels.

Which pull request: `--pr <number|url>`, else `links.pr`, else the one `gh` finds for
the current branch. With none of the three, the command exits 2 and says so.

**Staleness.** `spool plan stale [dir]` answers "is this plan still about this code?"
from the checkout, and from GitHub only when the checkout cannot answer (a shallow CI
clone). The verdict is a pure function of printed values:

| Code | Meaning | Tunable |
|---|---|---|
| `history-rewritten` | `links.commit` is no longer in the branch's history | no |
| `evidence-changed` | a file the packet cites changed since `links.commit` | no |
| `branch-moved` | the branch is more than `stale.commits` past `links.commit` | yes |
| `plan-aged` | `links.commit` is older than `stale.days` | yes |

A rewritten history and a changed cited file are stale at any tolerance: the first
means the plan's commit is gone, the second means the branch moved in exactly the code
the plan reasoned about. A plan that cannot be checked — no `links.commit`, no
repository, a commit this clone does not have and no GitHub answer — reads **unknown**,
never current.

```bash
spool plan pr [dir] [--pr <n|url>] [--dry-run] [--host <url>] [--json]
spool plan stale [dir] [--offline] [--json]
```

| code | `spool plan stale` | `spool plan pr` |
| ---- | ------------------ | --------------- |
| `0` | current | done, or nothing to do (not opted in, dry run, or GitHub unreachable) |
| `1` | stale | — |
| `2` | unknown | the command could not run (no plan, no pull request) |

**Rate limits and failure.** Every GitHub call goes through one runner
(`src/github/gh.mjs`), which shells out to `gh` — a status and a comment then post the
same way from a laptop and from CI, with the credential each already has, and spool
needs no GitHub App and no repository write access beyond comments and statuses. The
runner retries a secondary rate limit, a 5xx and a network failure with doubling
backoff; on a primary rate limit it waits for the reset the API reports, and refuses to
wait at all when that reset is more than a minute out. Anything it cannot post is
reported on stderr, and the command still exits 0.

```yaml
# .github/workflows/plan-gate.yml — after the gate step
- run: spool plan pr --pr ${{ github.event.pull_request.number }}
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### Pilot dataset (`spool pilot`, `pilot/dataset.json`, roadmap R6.1)

The dogfood pilot's measurement surface. `spool pilot collect` joins the hand-written
roster (`docs/pilot/scenarios.json`) to what the product already recorded and writes one
JSON document; `spool pilot report` prints it. How to run the pilot and how to read the
numbers is `docs/PILOT.md`.

**No pilot pipeline.** The collector emits nothing, stores nothing server-side and adds
no command an agent has to remember. Every field below is derived from three reads that
exist for other reasons — `GET /api/plans/{id}` (R4.1), `…/events` (R3.1) and
`…/revisions` (R3.4) — because R6.1's non-functional requirement is that pilot mechanics
must not distort what the pilot measures. The only hand-written input is the roster.

**`links.task` is the join key.** A packet's task id is what ties a recording to a
roster entry. A plan workdir whose task is absent from the roster is reported under
`unrostered`, never added: the sample is a decision, not whatever happened to be
recorded.

```jsonc
{
  "version": 1,
  "kind": "pilot-dataset",
  "generatedAt": "2026-08-17T03:18:43.647Z",
  "host": "https://spool.dev",          // null on --offline
  "window": { "closeWithinDays": 14 },  // the north-star window (R0.3)
  "roster": { "path": "…/docs/pilot/scenarios.json", "entries": 20 },
  "chains": [ /* one per roster entry, in roster order */ ],
  "summary": { /* the aggregates */ },
  "coverage": { /* per-scenario planned/live/decided/closed, plus gaps */ },
  "unrostered": [ { "dir": "…", "taskKey": null, "spoolId": null, "goal": "…" } ]
}
```

**A chain** is plan → decision → proof for one task:

| Field | Meaning |
|---|---|
| `taskKey`, `scenario`, `title` | the roster entry; `scenario` is one of `ui-feature`, `risky-refactor`, `bug-fix`, `agent-handoff` |
| `spoolId`, `watch`, `dir`, `status` | the published plan, and its lifecycle state |
| `outcome` | `proved`, `stopped` or `open`. `stopped` is declared in the roster: the lifecycle has no abandoned state |
| `publishedAt`, `revisions`, `rework` | revision 1's publication; the revision count; revisions beyond the first |
| `decisions[]` | every decision receipt: `{ revisionId, action, type, optionId, at, sincePublishMs }` — timed from the publication of the revision it was made against |
| `timeToFirstDecisionMs` | revision 1's publication to the first decision on the plan |
| `redirects`, `questions` | decisions that sent the plan back; questions asked |
| `implementation` | `{ startedAt, bypassed, policy, verdict, planValid }` — the gate receipt (R4.3) and the latest status verdict (R5.4) |
| `proofs[]`, `proof`, `deviations` | every `proof_published`, the one that closed the loop, and the length of its `deviations` array |
| `timeToProofMs`, `closedInWindow` | approval to proof, and whether that fits the window |
| `observations[]` | what the watching sessions recorded (R6.2, below); one row per revision |
| `sessionToDecisionMs`, `decidedBeforeEnd` | the session clock and the decision's position, from the first observation that carries them |
| `notes[]` | what this run could not measure, per row |

**Absent facts are null, never guessed.** A reader without a credential gets no event
log, so only the current revision is timed and every row says so in `notes`. A proof
read from the payload rather than the event log has no clock, so its `at` is null rather
than the time of the collect run. A packet nobody published reports `revisions: 0`, not
1: revision 1 exists once the server opened it, and counting a draft as a revision would
put an unpublished plan into the rework denominator.

**Rates name their denominator.** `proofRate` is over approved chains, `reworkRate` and
`redirectRate` over decided chains, and `northStar.rate` over approved chains — a proof
rate over every chain would be a different and weaker claim.

**Exit codes.** `0` it ran, `1` it ran and the sample is short of R6.1's coverage
targets (15–25 chains, at least 3 closed per scenario), `2` it could not run.

### Watch observation (`plan_observation_recorded`, roadmap R6.2)

What one watching session did with a plan spool, and what the watcher said about it
straight afterwards. The method, its thresholds and its limits are
`docs/PILOT-OBSERVATION.md`; this is the record's shape.

**It is a plan event, not a new store.** `POST /api/plans/{spoolId}/observations`
appends to the plan's own append-only log, so an observation joins to its chain on
`planSpoolId` + `revisionId` — the key every funnel already uses — and `spool pilot
collect` reads it through the `…/events` call it already makes. Gated by `plan.observe`:
the owner, their agent, and anyone invited to comment or decide. An unlisted link
watches and writes nothing.

**Request body.** `revisionId` is optional and checked: an observation about revision 1
must not be filed against revision 2, because the whole value of the record is that it
says what THIS cut of the plan did to a reader.

```jsonc
{
  "revisionId": "…",                    // 409 when the plan has moved on
  "trace": {
    "version": 1,
    "videoMs": 182000,
    "watchedMs": 121000,
    "reachedEnd": false,
    "positionMs": 141000,               // where the play head was
    "sinceFirstPlayMs": 402000,         // wall clock since the first frame played
    "chapters": [
      { "id": "risks", "lengthMs": 41000, "watchedMs": 4000,
        "coverage": 0.1, "rewatchedRatio": 0, "passes": 1 }
    ]
  },
  "decision": { "action": "approve", "atVideoMs": 141000,
                "beforeEnd": true, "sinceFirstPlayMs": 402000 },
  "note": {                             // optional; the three clicks are required in it
    "perspective": "decider",           // operator | decider | reviewer — self-reported
    "effect": "quality",                // quality | presentation | neither
    "wouldRequire": "yes",              // yes | no | unsure
    "faster": "…", "distrust": "…", "stillNeeded": "…"   // ≤ 280 characters each
  }
}
```

**The verdicts are re-derived, never believed.** `skipped` is `coverage <
SKIPPED_MAX_COVERAGE` (0.5) and `rewatched` is `rewatchedRatio >= REWATCH_MIN_RATIO`
(0.2), both recomputed server-side from the coverage the client sent, both defined in
`web/lib/planWatchTrace.ts`. The vocabulary and the parsers live in
`web/lib/planObservations.ts`, which is isomorphic because the note card renders from
it; the authorized write is `web/lib/planObservationLog.ts`. `watchedRatio` is recomputed from `watchedMs / videoMs`. A
chapter id outside the five stable ones is dropped rather than stored: a sixth id would
silently split a metric.

**Two receipts per session is normal.** The trace posts the moment a decision lands, so
a watcher who closes the tab still leaves the measurement behind; the note posts if and
when it is answered. Both are honest history in an append-only log, and the collector
takes one row per revision, preferring the one that carries a note.

**It never fails a decision.** The write is fire-and-forget from the watch page. An
instrument that could block what it measures would be measuring itself.

**PostHog gets counts, never sentences.** The route also emits `plan_watch_observed`
(docs/PLAN-SPOOLS-ANALYTICS.md) carrying `chaptersSkipped`, `chaptersRewatched`,
`decidedBeforeEnd`, `watchedRatio` and `chapterCount`. The written answers stay in the
plan's event log, behind `plan.read_events`.

### Assumption register (`docs/pilot/assumptions.json`, roadmap R6.2)

The beliefs Plan Spools rests on, with the thresholds that would settle them, written
down before the data exists. `spool pilot synthesize` scores them against the dataset and
writes the prioritised retained / changed / removed list to `pilot/assumptions.md`.

```jsonc
{
  "version": 1,
  "assumptions": [{
    "id": "risks-carry-the-decision",
    "claim": "The risks chapter is what a decision turns on, so it is watched.",
    "source": "docs/PLAN-SPOOLS-PRD.md FR-2 and FR-7",
    "weight": 3,                                   // 1–3: how load-bearing the belief is
    "metric": "chapterSkipRate",                   // from the closed catalog only
    "arg": "risks",                                // required by the chapter metrics
    "supportIf": { "op": "<=", "value": 0.2 },
    "rejectIf":  { "op": ">",  "value": 0.5 },
    "minSample": 5,
    "quotes": ["distrust"],                        // note fields to print verbatim
    "ifRemoved": "…what changes if this belief is wrong"
  }]
}
```

**Four rules, enforced by the validator.** A metric must be one of the catalog in
`src/pilot/assumptions.mjs`; both thresholds are required, because a belief with no
refutation condition is unfalsifiable; the thresholds may not overlap, or the verdict
would depend on which check ran first; and `minSample` is required, because below it the
verdict is `untested` however decisive the number looks.

**Verdicts.** `retained` satisfies `supportIf`, `removed` satisfies `rejectIf`, `changed`
falls between them, `untested` is under the sample floor. `priority` is `weight ×
impact` (removed 3, changed 2, retained 1, untested 0), so the list opens on the
load-bearing beliefs the evidence moved.

**Every verdict names its chains**, and every quote names the chain it came from — the
R6.2 traceability requirement, made structural. Sentences are quoted, never classified.

**Exit codes.** `0` at least one assumption was answerable, `1` every one is still
`untested`, `2` it could not run.

### Reliability signals (`plan_operation`, `.spool/reliability.jsonl`)

Roadmap R6.3. Eight things can fail between "an agent proposes work" and "a proof
closes the loop", and each one has one name, one closed reason vocabulary, one
target, and one runbook. The contract is `web/lib/planReliability.ts`, with the CLI
twin in `src/reliability/signals.mjs`; the numbers and the recovery steps are in
`docs/PLAN-SPOOLS-RELIABILITY.md` and `docs/PLAN-SPOOLS-RUNBOOKS.md`.

| operation | fails when | measured by |
| --- | --- | --- |
| `record` | a take never captures | the local journal |
| `render` | captured input never becomes `final.mp4` | the local journal |
| `publish` | media lands and the plan never opens | both |
| `decision` | a submitted decision is refused | the server |
| `authorization` | a plan endpoint denies a request | the server |
| `agent_read` | an agent cannot learn the decision status | both |
| `stale_plan` | the branch moved past the plan | both |
| `evidence_link` | a stored evidence descriptor stops resolving | the server |

**Outcome.** `ok`, `retried` or `failed`. `retried` means it worked because a retry
or an idempotent replay covered for a failure; it counts as a success against the
target and stays visible as its own number.

**The server signal.** One PostHog event, `plan_operation`, carrying only
`operation`, `outcome`, `reason`, `severity`, `attempts`, `durationMs`, `count`,
`weight`, `endpoint`, `httpStatus`, `spoolId`, `planSpoolId`, `revisionId`,
`projectId`, `actorType` and `environment`. A closed allowlist, like the analytics
catalog: no property holds free text, so a signal cannot carry a diff, a narration
line, a path, an email or an IP. `severity` and `weight` are stamped by the
contract and the emitter, never by a call site. A `reason` outside that operation's
vocabulary is dropped rather than sent.

**Sampling.** Successes are sampled (`PLAN_RELIABILITY_SAMPLE`, default 0.1), and
so are `info` failures — anonymous denials are the flood case, and sampling them is
what stops a request storm becoming an emission storm. Everything else is kept.
Every sent signal carries `weight` (1, or `1 / rate` when sampled), and every query
sums `weight` instead of counting rows.

**The local journal.** `<repo>/.spool/reliability.jsonl`, one line per attempt:
`{at, operation, outcome, reason, severity, attempts, ms, target, detail}`.
`target` is the workdir slug, never a path. `detail` is the error message, and it
never leaves the machine. The file rotates at 1 MB, every write is swallowed, and
`SPOOL_RELIABILITY=off` disables it. Read it with:

```bash
spool reliability [dir] [--since 7d] [--json]   # 0 nothing breached · 1 breached · 2 no data
```

**Retry and idempotency.** One helper, `src/reliability/retry.mjs`: retry only a
connection that never landed, a 408, a 429 or a 5xx; never a 4xx; bounded attempts,
bounded per-attempt timeout, capped exponential backoff with full jitter, and
`Retry-After` honoured and capped. A retried write reuses ONE idempotency key —
generating a key per attempt would turn a retry into a second write. The reserving
`POST /api/publish` call is not idempotent and is therefore not retried.

## console.jsonl (spool record → spool share)

Browser telemetry captured during recording, one JSON object per line, times in
seconds relative to video t=0 (same clock as timeline.json):

```json
{"t": 3.41, "kind": "console", "level": "error", "text": "Uncaught TypeError: ..."}
{"t": 5.02, "kind": "pageerror", "text": "ReferenceError: foo is not defined"}
{"t": 7.80, "kind": "requestfailed", "text": "GET http://localhost:4747/api/x net::ERR_..."}
```

Levels for kind=console mirror Playwright's msg.type(). Always written (empty file
when nothing fired) so consumers can rely on its presence.

## signals.jsonl (spool record / spool live → spool recut)

What the session DID, one JSON object per line, on the same clock as timeline.json.
Capture writes one continuous take and this log; the cut is derived from the log rather
than baked into the recording, so a wrong boundary is re-derived instead of re-recorded:

```json
{"t": 0.01, "kind": "navigated", "url": "http://localhost:3000/inbox"}
{"t": 4.20, "kind": "click", "x": 228, "y": 32, "target": "#inbox", "text": "Inbox"}
{"t": 4.71, "kind": "settle"}
{"t": 9.30, "kind": "marker", "name": "approve-it", "chapterId": "approach", "narration": "..."}
```

`settle` fires once the network has been quiet for 500ms. `marker` is written by
`POST /marker`, by `POST /step`, and by every scripted step boundary — which is why a
scripted take is re-cuttable too.

Boundary rules (`src/record/signals.mjs`): a cut opens at a marker, at a click that causes
a navigation within 1.5s, and at a navigation nothing clicked for. Inferred cuts closer
together than `--min-step` (default 2.5s) fold into the one before them; a marker never
folds and never loses its name. Steps carry `source` so a reader can see where a boundary
came from. Windows slice the video from each step's own `start`, so a dropped step leaves
a hole in the take and its footage never reaches the output.

## share/ bundle (spool share → any consuming agent)

The agent-consumable artifact. `spool share <workdir>` (auto-run at the
end of `spool build`) writes:

```
spool/<slug>/share/
├── spool.json         # the single machine-readable index (below)
├── transcript.txt     # "[mm:ss] narration" per step — cheap skim for an agent
├── frames/step_NN.png # one keyframe per step (mid-step, post-click when clicks exist)
├── console.jsonl      # copied from the workdir
├── plan.json          # Plan Spools only (see "Plan Spools")
├── evidence.json      # Plan Spools only
└── reply.json         # reply spools only (see "Replies")
```

`spool.json`:

```json
{
  "version": 1,
  "kind": "spool",
  "title": "Finishing Lab walkthrough",
  "url": "http://localhost:4747",
  "video": "../final.mp4",
  "duration": 29.0,
  "rate": 1,
  "format": "wide",
  "width": 1920,
  "height": 1080,
  "voice": { "engine": "openai", "voice": "alloy" },
  "steps": [
    {
      "i": 0,
      "name": "open-board",
      "chapterId": "context",
      "narration": "Here's the finishing lab — every rep gets tracked on this board.",
      "start": 1.02,
      "end": 6.10,
      "clicks": [ { "x": 512, "y": 340, "t": 2.41 } ],
      "frame": "frames/step_00.png"
    }
  ],
  "console": { "errors": 0, "warnings": 2, "log": "console.jsonl" }
}
```

Consumption: `spool read <workdir-or-share-dir>` prints an agent-oriented digest
(title, url, per-step narration + timings + frame paths, console error summary) so
a receiving agent can orient in one command and Read only the frames it needs.
On a Plan Spool, `kind` is `"plan"` and a `plan` object carries the packet summary the
watch page renders (goal, outcome, approach, alternatives, assumptions, risks, decision,
evidence, links). The mutable decision status is never stamped into this immutable file:
`spool read --plan` and the watch page read it from the host.

`steps[].chapterId` is copied from `timeline.json` unchanged (Plan Spools only, additive);
`spool read` prints a `chapters:` block with the range each chapter runs in. See "Plan
Spools" → "Chapter mapping".

Paths inside spool.json are share-dir-relative; the bundle is self-contained apart
from the ../final.mp4 pointer. `format`/`width`/`height` are additive (version stays 1):
`format` is copied from `render.json`, the dimensions are probed off the deliverable, and
all three are absent on bundles built before the vertical format shipped.

**Plan Spool lineage (additive, version stays 1).** `kind` is `"spool"` for a walkthrough,
`"plan"` for a Plan Spool, or `"proof"` for a Proof Spool. The same `plan` block also
carries the lineage ids beside the packet summary — on a plan they name that plan's own
revision; on a proof they name the approved plan revision being proved, and the proposal
fields are absent:

```json
{
  "kind": "plan",
  "plan": {
    "planSpoolId": null,
    "revisionId": "rev_01H...",
    "revisionNumber": 2,
    "parentRevisionId": "rev_01H...",
    "projectId": "aaarnv/spool",
    "goal": "…"
  }
}
```

A **reply spool** carries a `reply` block instead (roadmap R4.2), pointing at
`share/reply.json` and repeating its lineage — the parent plan, the revision it answers,
the anchors, the summary. Its `kind` stays `"spool"`, or `"proof"` for a proof reply: a
reply is a recording, not a proposal of its own. The block is what makes a reply work on
a published link, and like the `plan` block it never carries a mutable status. See
"Replies".

A **recap spool** carries a `recap` block and `kind: "recap"` (roadmap B2). Nothing
recorded it and nobody authored it: the platform rendered it from a merged pull request,
so the block is the pull request's identity and nothing else.

```json
{
  "kind": "recap",
  "recap": {
    "repo": "aaarnv/spool",
    "number": 41,
    "url": "https://github.com/aaarnv/spool/pull/41",
    "title": "Cap the recap diff",
    "author": "octocat",
    "baseRef": "master",
    "mergedAt": "2026-08-24T00:00:00Z",
    "mergeCommitSha": "…",
    "additions": 524,
    "deletions": 166,
    "changedFiles": 27
  }
}
```

The DIFF the script was written from is deliberately absent, from the block and from the
published sources. A blob is readable by anyone holding the link, and a private
repository's code must not become readable through a spool url — the pull request url is
where a viewer with access goes to read it. A recap never carries a `plan` block: it
reports work that already merged, so it opens no decision. See "Merged-PR recaps".

`planSpoolId` may be omitted on a plan: the plan is that spool. Only `revisionId` is
required to emit lifecycle events, and the ids are additive — a plan bundle written
before they shipped still renders. The semantic packet itself lands in `plan.json`
(roadmap R1.1); the block never carries the mutable decision status. `/api/publish`
reads the ids to emit the lifecycle events in `docs/PLAN-SPOOLS-ANALYTICS.md`; a bundle
without them publishes exactly as before.

## Plan Spools (plan.json, evidence.json, share/plan.json)

A **Plan Spool** is a proposal a human watches and an agent reads. The video orients
the reviewer; `plan.json` carries the precision. One artifact serves both, so the
summary on the watch page and the packet an agent acts on cannot drift.

A workdir becomes a Plan Spool by containing `plan.json`. Validation is enforced by
`src/plan/schema.mjs`, which is the single source of truth for this section.

### plan.json

```jsonc
{
  "version": 1,                       // required, integer; the major version
  "kind": "plan",                     // required, "plan"
  "goal": "Add timestamped questions to a published spool.",   // required
  "outcome": "A reviewer can ask a question against a video moment.",  // required
  "currentState": [                   // optional
    {"claim": "Watch pages have an Ask panel but no durable comments.",
     "evidence": ["ev-askpanel"], "chapterId": "context"}
  ],
  "approach": [                       // required, >= 1 item
    {"id": "data", "summary": "Add comment and anchor records.",
     "chapterId": "approach", "evidence": ["ev-schema"]}
  ],
  "alternatives": [                   // optional
    {"id": "thread-per-spool", "summary": "Use an unanchored thread only.",
     "tradeoffs": ["Simpler", "Loses moment-level context"]}
  ],
  "noAlternativesReason": "…",        // REQUIRED when alternatives is absent or empty
  "assumptions": ["Only owner and invited reviewers can decide in v1."],  // optional
  "risks": [                          // required; a string, or a claim with evidence
    "Public links need a clear permission model.",
    {"claim": "The anchor may drift on re-record.",
     "evidence": ["ev-schema"], "chapterId": "risks"}
  ],
  "decision": {                       // required
    "type": "approval",               // "approval" | "selection"
    "prompt": "Approve the anchored-comment approach.",
    "options": ["approve", "redirect", "ask-question"],
    "evidence": ["ev-askpanel"]       // optional
  },
  "links": {"task": null, "repo": "aaarnv/spool", "branch": "spl/spl-12",
            "commit": "abc123", "pr": null},                              // required
  "chapters": [                       // optional; defaults to the five canonical IDs
    {"id": "context", "title": "What exists today"},
    {"id": "decision", "title": "What we need from you"}
  ]
}
```

Rules the validator enforces:

- **Chapter IDs are a closed set**: `context`, `outcome`, `approach`, `risks`,
  `decision`. They are semantic anchors, never timeline array positions. Any
  `chapterId` must name a declared chapter (or a canonical one when `chapters` is
  absent), and a declared `chapters` list must include `decision`.
- **`approach[].id` is kebab-case and unique.** Questions, proofs, and revision
  diffs anchor to it, so it must stay stable across revisions.
- **Absence of alternatives is a statement, not a silence.** With no
  `alternatives`, `noAlternativesReason` is required (for example, "no credible
  alternative considered: the schema is fixed by the existing contract"). Setting
  both is an error.
- **Decision options are actionable.** Each option is `approve`, `redirect`,
  `ask-question`, `needs-input`, or `alternative:<id>` naming a declared
  alternative. An `approval` decision must offer `approve`; a `selection`
  decision must offer at least one `alternative:<id>`.
- **A risk is a string or a claim.** A claim (`{"claim": …, "evidence": […],
  "chapterId": …}`) can cite evidence; a plain string cannot. The published copy
  normalizes both to claims.
- **`links` values are strings or `null`.** `null` means "does not apply"; a
  missing key and a null key read the same. `links.pr` and `links.issue` are the
  two a tool acts on, and each must name its own kind — see "GitHub
  integration". `links.branch` and `links.commit` are the plan's source
  revision, which is what staleness is measured against.
- **Unknown top-level fields warn, never fail** — a newer authoring tool may add
  fields this CLI has no opinion about.

### JSON Schema mirror

`src/plan/plan.schema.json` and `src/plan/evidence.schema.json` are JSON Schema
(draft 2020-12) mirrors of the same contract, so a tool that is not the spool CLI
can validate a packet with an off-the-shelf validator. Both files ship in the npm
package.

They are **generated**, never hand-edited: `src/plan/json-schema.mjs` builds them
from the validator's exported constants, `npm run schema` writes them, and
`test/plan-json-schema.test.mjs` fails when a committed file is stale, when a
schema enum stops matching a validator constant, or when schema and validator
disagree about accepting a packet. Add a chapter ID, an evidence kind or a
decision action to `src/plan/schema.mjs`, run `npm run schema`, and commit both.

The schemas carry the **error-level structural rules only**, including the
per-kind `ref` patterns (a commit SHA, an `http(s)` URL, a repository-relative
path), which come from `REF_PATTERNS` in `src/plan/evidence.mjs`. Two classes of
rule stay CLI-side because JSON Schema cannot express them:

- warnings (length limits, unknown top-level fields, empty `risks`, unpinned
  evidence, over-long excerpts, unedited template placeholders)
- rules that need resolution or another field: private hosts and URL credentials,
  a line range that ends before it starts, an excerpt on a private descriptor,
  evidence IDs resolving to `evidence.json`, unique IDs, `alternative:<id>`
  options naming a declared alternative, an `approval` offering `approve`, a
  `selection` offering an alternative, and `chapterId` restricted to the plan's
  own declared chapters rather than the canonical five

So a packet that passes the schema can still fail `spool lint`. The CLI validator
stays the gate; the schema is the portable approximation of it.

### Versioning

`version` is the major version. A reader that meets a `version` higher than it
understands **rejects the packet loudly** and reports nothing else about it: on an
unknown shape every other diagnostic is guesswork. `version` is currently `1` for
both `plan.json` and `evidence.json`.

### evidence.json

Evidence is **referenced, never copied**:

```jsonc
{
  "version": 1,
  "kind": "evidence",
  "items": [
    {"id": "ev-askpanel",              // kebab-case, unique
     "kind": "file",                   // file | url | image | test | commit | console
     "label": "Existing AskPanel implementation",
     "ref": "web/app/l/[id]/AskPanel.tsx",   // path, URL, SHA, or command
     "revision": null,                 // git SHA the ref was read at
     "lines": [12, 40],                // optional, file/image only: [start] or [start, end]
     "summary": "The panel already posts to /api/questions.",  // optional, one plain-language line
     "excerpt": "export function AskPanel() {",  // optional, short, bounded
     "visibility": "public",           // optional: "public" (default) | "private"
     "chapterIds": ["context"]}
  ]
}
```

Which plan fields may cite evidence IDs: `currentState[]`, `approach[]`,
`risks[]` (in claim form), `alternatives[]`, and `decision`. A reference that no
descriptor declares is an error, and so is a reference in a workdir with no
`evidence.json`: the claim promises a source the packet cannot resolve.

**A descriptor earns its place two ways**: a claim cites it, or it names a
`chapterIds` chapter. Either is a declaration of where it belongs in the plan; a
descriptor with neither is decoration, and warns (`unused-evidence`). The second
route is what lets a collector attach twelve diffs without forcing twelve
citations — an agent that has to cite everything attaches less proof.

**Ref rules are per kind**, because a ref becomes a link on a page a stranger can
open (`src/plan/evidence.mjs` owns them):

| kind | `ref` is | rejected |
| --- | --- | --- |
| `file`, `image` | a repository-relative path | absolute or `~` paths, `..` segments, backslashes, URLs |
| `url` | an absolute `http(s)` URL | other schemes, `user:password@`, private hosts (`localhost`, RFC1918, `*.internal`, a name with no dot) |
| `commit` | a git SHA, 7 to 40 hex characters | branch names and tags: they move |
| `test`, `console` | the single-line command that produced the output | line breaks and control characters |

A ref that names a private host or an absolute path is an error **unless** the
descriptor declares `"visibility": "private"`. A private descriptor publishes its
label and nothing else, so declaring it is how an author says "this source is
real, and you cannot open it".

**Pinning.** A `file` or `image` descriptor without `revision` and without
`links.commit` warns (`unpinned-evidence`): `main` moves, so an unpinned link
would show a reviewer something the agent never read.

**Summaries.** `summary` is one plain-language sentence about what the source
showed. It is what a card renders **first**, so code and command output stay one
click away — the v1 product default is plain language first, raw source on demand.
It is bounded to **240 chars** on one line (line breaks collapse), redacted when
published, and forbidden on a private descriptor, where the `label` carries the
plain language instead. A descriptor with a summary publishes as `available` even
when nothing links to it: a reviewer can read what it showed.

**Excerpts.** `excerpt` is optional, and it is a reading aid beside the ref, never
a replacement for it: a reviewer without repository access still learns something.
It is truncated to **20 lines / 1200 chars** and redacted when published, and it
is forbidden on a private descriptor. Product default (v1): show concise excerpts
only where repository access permits; otherwise show the label and the link.

**Size caps.** Per descriptor the caps are hard: publishing truncates. Per plan
they are **40 descriptors** and **24000 chars** of summaries plus excerpts
together; `spool plan evidence` refuses to add past them and names what it
refused, and `spool plan validate` warns (`too-many-evidence`,
`evidence-too-large`) for a hand-authored bundle. Publishing never drops a
descriptor a claim cites — that would turn a cited claim into a dangling one.

**Bundled refs.** A `file` or `image` ref that resolves **inside the spool
workdir** — a keyframe, a captured artifact — is a bundle artifact, not a
repository file. `resolveRefs` marks it, and no repository permalink is built for
it: the workdir is gitignored, so the link would 404. It publishes `available`
with `url: null` and travels in the share bundle.

### Evidence adapters (spool plan evidence)

An agent that changed files, ran a test and recorded a browser has already
produced the proof behind its claims. `spool plan evidence <workdir>` attaches it
as descriptors, so the agent never retypes it and never pastes it unredacted.

```bash
spool plan evidence <workdir> [--test <cmd>]…
                              [--base <ref>] [--chapter <id>] [--dry-run] [--json]
```

| collector | writes | `ref` | `summary` | `excerpt` |
| --- | --- | --- | --- | --- |
| `diff` | one `file` descriptor per changed file, `ev-diff-<slug>` | the repo-relative path, pinned to HEAD | `Changed web/lib/plans.ts (+42 −7).` | that file's diff hunks |
| `commit` | one `commit` descriptor, `ev-commit` | the git SHA | `Branch spl/spl-32 at b227141: <subject> — 9 changed files.` | the changed-file list |
| `--test <cmd>` | one `test` descriptor, `ev-test-<slug>` | the command | `npm test passed (exit 0) in 4.2 s.` | the **tail** of stdout+stderr |
| `console` | one `console` descriptor, `ev-console` | the recording command | the error/warning tally over N events | the first errors, `[t] kind: text` |
| `keyframes` | one `image` descriptor per frame, `ev-frame-<slug>`, plus `ev-recorded-url` | the frame path (bundled); the page URL | `The recorded screen at step 3, "…".` | — |

- **Diff, commit, console and keyframes always run**, and each skips itself when its
  source is absent, so there is nothing to pick between. `--test` stays out of that:
  it runs a command the agent must name.
- **The tail, not the head**, for a test run: the failing assertion and the totals
  line are at the end, so head truncation would publish the setup and drop the
  result the claim rests on.
- **A clean console is evidence too** — it is the proof behind "this breaks
  nothing on the page" — so the descriptor is written either way, with the tally
  as its summary.
- **A dev-server URL** is written `"visibility": "private"`: it is real, and a
  reviewer cannot open it, so it publishes as withheld rather than as a dead link
  and a hint about the network.
- **Re-collecting replaces a descriptor in place** by id, so a claim citing
  `ev-test-npm-test` keeps citing the same run after the test runs again. Nothing
  a collector wrote earlier, and nothing hand-authored, is ever removed.
- **Caps are never silent.** Per-collector budgets (12 diffs, 8 keyframes, 12
  console errors) and the per-plan caps both print what they refused: "12 of 300
  files" and "12 files" are different claims.
- **The diff cap keeps the BIGGEST changes**, ranked by git's line counts and
  tie-broken by path. A cap that took files in path order published `.github/` and
  dropped `src/` on any change wide enough to reach it. A file git gave no counts
  for — a binary, an untracked one — is ranked by the lines its own patch changes,
  so a new module is never dropped in favour of a one-line edit.
- **A packet that cites nothing is called out.** When `evidence.json` declares
  descriptors and no claim in `plan.json` cites any of them, `validatePacket` warns
  ONCE — `uncited-evidence`, on `evidence.json:items` — and `spool plan evidence`
  repeats that one warning in the run that caused it. Descriptors nothing cites are
  attachments, not evidence. One citation anywhere silences it: the per-descriptor
  `unused-evidence` rule stays quiet for chapter-anchored items, so this is the only
  pressure left to connect a source to the sentence it backs. `--strict` turns it
  into an error, like every other packet warning.
- **Nothing secret is published.** Every label, ref, summary and excerpt goes
  through the redaction rules in `src/plan/evidence.mjs` at collection time, so a
  credential never reaches the workdir file, let alone the bundle. The test
  command inherits the environment because tests need it; the environment itself
  is never read or published — only the command's own output, redacted.
  Redaction covers the SPACE-SEPARATED form as well as `=` and `:`
  (`aws_secret_access_key wJal…`, `--token 8f3a…`), because a CLI flag and a
  key-space-value config line are where a collector actually meets a credential.
  The space-separated rule guards the VALUE — at least 12 characters of the token
  alphabet, and at least one digit or symbol among them — so "the password is
  required" keeps its next word. The adversarial battery in
  `test/plan-collect.test.mjs` runs every shape through all four collectors, and
  asserts that prose survives untouched.
- **Every collector anchors what it writes to a chapter**, so a collected packet
  passes `spool plan validate --strict` before a single citation is written:
  the diff → `approach`, the commit → `context`, `--test` → `outcome`,
  the console → `risks`, a keyframe → its own step's chapter (else `outcome`), the
  recorded URL → `context`. `--chapter <id>` overrides all of them for that run.
- `--base <ref>` diffs `base...HEAD` (what a pull request shows) instead of the
  working tree. `--dry-run` reports and writes nothing.

Exit codes: `0` collected, `1` nothing valid to write, `2` the workdir has no
`plan.json` (evidence backs a plan's claims). The adapters are pure
(`src/plan/collect.mjs`); the git, child-process and workdir reads live in
`src/plan/collect-sources.mjs`.

### Validation gate

`plan.json` is validated **before any stage that costs time**: `spool dry`,
`spool record`, `spool live`, `spool vo`, `spool build`, `spool finish` (local and
`--cloud`). An invalid packet exits `1` and prints one line per problem, each naming
the offending field path (`approach[1].id`, `decision.options[0]`). `spool lint`
runs the same validator, so an invalid packet also blocks `spool publish`.

An invalid plan is an authoring problem, not a render problem. It must never cost a
recording or a VO run.

### Template placeholders

Every placeholder string in `templates/plan.json` and `templates/evidence.json`
starts with the marker `TODO:`. Any packet string still carrying that marker is a
**warning** (`unedited-template`) naming the field. A scaffolded packet is therefore
valid but never silent: structure alone cannot catch "the exact action the reviewer
must take", which is a well-formed prompt and a worthless one. `spool plan validate
--strict` turns these into errors, which is what CI should run.

### spool plan (the command namespace)

A Plan Spool is an ordinary workdir plus `plan.json`, so `spool plan` sits beside the
media commands instead of replacing them. All three work offline, with no account and
no web app.

```bash
spool plan init <slug> --goal "..." [--task <url-or-id>] [--outcome "..."] [--pr <url-or-number>] [--issue <url-or-number>] [--dir <path>] [--force]
spool plan evidence <workdir> [--test <cmd>] [--base <ref>] [--chapter <id>] [--dry-run] [--json]
spool plan validate [dir] [--json] [--strict]
spool plan generate <workdir> [--steps] [--url <u>] [--title <t>] [--force] [--json]
spool plan build <workdir> [--strict] [same flags as spool build]
spool plan pr [dir] [--pr <n-or-url>] [--dry-run] [--json]
spool plan stale [dir] [--offline] [--json]
```

- **`init`** writes `spool/<slug>/plan.json` + `evidence.json` from the templates,
  with `goal`, `links.task` and `outcome` filled in from the flags. `links.repo`,
  `links.branch` and `links.commit` are read from the checkout in the current
  directory — that commit is what evidence permalinks pin to, and no agent fills it
  in by hand. Outside a checkout they stay `null` and the packet is still valid.
  `init` refuses to overwrite an existing `plan.json` without `--force`.
- **`evidence`** collects the proof the agent already produced — diffs, the commit,
  console errors, keyframes — into `evidence.json`. Every collector runs; each skips
  itself when its source is absent. `--test <cmd>` additionally runs a command and
  attaches its result. See "Evidence adapters" above.
- **`validate`** prints the terse report (what the plan asks for, then one line per
  problem, each naming the field) or, with `--json`, the diagnostics document below.
  `dir` defaults to `.`.
- **`generate`** turns a valid packet into `plan.script.json` (see below) and, with
  `--steps`, the `steps.mjs` that records it.
- **`build`** validates first, then runs exactly the `spool build` pipeline. On an
  invalid packet it stops before recording and before voiceover.
- **`pr`** and **`stale`** are the GitHub surface: the comment a reviewer finds the
  plan from, and the check that says whether the plan is still about this code. Both
  are documented in "GitHub integration", and neither can fail a build.

Exit codes are stable, and `spool plan build` uses the same three:

| code | meaning |
| ---- | ------- |
| `0` | packet valid (warnings allowed unless `--strict`) |
| `1` | packet present and invalid |
| `2` | no `plan.json` here: this workdir is not a Plan Spool |

`--json` writes one document to stdout. Keys only ever get added, never repurposed:

```jsonc
{
  "ok": true,                  // the only question a script asks
  "dir": "/abs/path/to/workdir",
  "present": true,             // false = not a Plan Spool (exit 2)
  "exit": 0,                   // the process exit code, so a captured report is self-contained
  "summary": {                 // null when plan.json could not be parsed
    "version": 1, "goal": "…", "outcome": "…",
    "chapters": ["context", "…"], "approach": ["data"], "alternatives": [],
    "decision": {"type": "approval", "prompt": "…", "options": ["approve"]},
    "evidence": 2
  },
  "errors": [{"path": "plan.json:decision.options", "code": "missing-approve", "message": "…"}],
  "warnings": [{"path": "plan.json:outcome", "code": "unedited-template", "message": "…"}]
}
```

`path` is `<file>:<field>`, the same path the human report prints, so a diagnostic
points at the exact field to fix in the exact file.

### plan.script.json (generated narration outline)

`spool plan generate <workdir>` turns a **valid** packet into `plan.script.json`: the
narration outline, one visual source per chapter, and the decision card. One artifact
drives both authoring paths — `--steps` emits a scripted `steps.mjs` from it, and a live
session replays its `chapters[].step` bodies through `POST /step`.

```jsonc
{
  "version": 1,
  "kind": "plan-script",
  "generator": "deterministic",      // "deterministic" | "llm-refined"
  "goal": "…",                       // copied from plan.json, for the title card
  "voice": {"profile": "direct-technical", "instructions": "…TTS register…"},
  "visualLanguage": "code-forward",
  "estimatedSeconds": 68.4,          // sum of the chapter estimates
  "chapters": [
    {"id": "context",                // a plan.json chapter ID, in plan order
     "title": "What exists today",
     "narration": "First, where things stand today. …",
     "words": 34,
     "estimatedSeconds": 13.7,       // words / 2.6 + 0.6s settle
     "visual": {"kind": "code",      // browser | code | image | terminal | card
                "source": "evidence:ev-askpanel",   // evidence:<id> | url:<u> | plan:<chapterId> | authored
                "label": "Existing AskPanel implementation",
                "ref": "web/app/l/[id]/AskPanel.tsx",
                "selector": null,
                "zoom": "none"},
     "sources": ["evidence:ev-askpanel", "plan.currentState[0].claim"],
     "step": {"name": "context", "chapterId": "context", "narration": "…", "zoom": "none"}},
    {"id": "decision", "…": "…",
     "card": {"type": "approval", "prompt": "…",
              "options": [{"id": "approve", "label": "Approve"}]}}
  ]
}
```

**The generator never invents a claim.** Author sentences are copied verbatim; the
generator only adds fixed lead-ins that carry no facts. Every chapter records the packet
paths it was built from in `sources` (`plan.<field>[i]…` or `evidence:<id>`), and the
quality lint resolves each one. A source that resolves to nothing is an `invented-source`
error, so a fabricated claim fails the lint instead of reaching a reviewer.

Generation is **deterministic**: the same packet and style always serialize to the same
bytes. A model pass then runs over it by default (`src/plan/outline-llm.mjs`, `gpt-5`, or
`SPOOL_PLAN_MODEL`), and may only rewrite the *wording* of a chapter. Every way it can fail
— no `OPENAI_API_KEY`, an unreadable reply, a network error — falls back to the
deterministic script, which is why it needs no flag. A rewrite is discarded per chapter —
keeping the deterministic text and reporting a warning — when it changes the chapter set, drifts
more than 35% in length, or introduces an identifier, path or number the packet does not
contain. A refined script that fails the quality lint is dropped entirely. The artifact
records which path produced it in `generator`.

**Voice and visual language** are the editorial knobs. They have no flags — a project picks
one register and keeps it — and resolve `SPOOL_PLAN_VOICE`/`SPOOL_PLAN_VISUALS` >
`planVoice`/`planVisuals` in `~/.spool.json` > default:

| Voice | Reads like |
| --- | --- |
| `direct-technical` (default) | An engineer briefing an engineer. |
| `calm-client-ready` | A lead walking a stakeholder through a proposal. |

| Visual language | Shows |
| --- | --- |
| `code-forward` | Source, diff, and test output first; an evidence-backed visual is named in the narration ("On screen: …"). |
| `product-forward` (default) | The running product first; file names stay out of the narration. |

`voice.instructions` is the TTS register. `spool vo` uses it for a workdir that has a
`plan.script.json`, between an explicit register and the format default, so the take is
read the way the plan was generated.

**Choosing a chapter's visual.** The generator picks the first evidence descriptor that
names the chapter in `chapterIds` (or is referenced by one of its claims), ordered by the
visual language's preference. An author overrides it with an additive `visual` hint on the
chapter in `plan.json` — the packet validator ignores the field, the generator checks it:

```jsonc
{"id": "approach", "title": "How we build it",
 "visual": {"kind": "browser", "url": "http://localhost:3000/plans",
            "selector": ".plan-card", "label": "The plan list"}}
```

`{"evidence": "<id>"}` points the chapter at a descriptor instead. A chapter with no
evidence and no hint gets a `card` visual and a lint warning.

**Quality lint.** `lintPlanScript` runs inside `spool plan generate` and again in
`spool lint` (check name `plan-script`), so a bad outline is diagnosable from the lint
report alone:

| Level | Check |
| --- | --- |
| error | a missing `context`, `approach`, `risks` or `decision` chapter |
| error | fewer than 3 or more than 6 chapters |
| error | an estimate over 120s (the format's promise), an empty narration, a missing visual |
| error | `invented-source`: a `sources` path that resolves to nothing, or an undeclared evidence ID |
| error | `decision-drift`: the card no longer matches `plan.json` `decision` |
| warn | an estimate under 45s, a chapter over 60 words or under 8, an em dash, a card-only visual |

A failing generation writes nothing: the report names the chapter and the field to change.

`spool plan generate --steps` writes a scripted `steps.mjs` with one step per chapter,
the chapter ID as both `chapterId` and the step name, and a driver body that only does what the visual asks
(navigate for a `browser` visual, wait/hover for a `selector`, hold otherwise). It refuses
to overwrite a `steps.mjs` it did not write — a hand-authored script or a live snapshot —
unless `--force` is passed. `card` visuals hold the current frame until the plan visual
templates land (R2.2).

### Chapter mapping (plan.json chapter → video range)

A reviewer clicks a part of the plan and the player jumps to the moment the agent
explained it. One field carries that: **`chapterId` on a step record**.

```
plan.json chapters[].id  ──┐
                           ├─ steps.mjs step / POST /step  ── chapterId
                           ├─ timeline.json steps[]        ── chapterId   (recording clock)
                           ├─ retimed window               ── chapterId
                           └─ share/spool.json steps[]     ── chapterId   (output clock)
```

Rules:

- **`chapterId` is the only anchor.** `steps[i].name` keeps its meaning everywhere (tour
  stops, keyframes, logs) and is free to change; renaming a step never breaks the mapping.
- **Never an index.** A chapter is named by its stable ID, never by a position in
  `timeline.json`. `timeline.json` stays the recording-clock source of truth, and
  `plan.json` carries no times at all.
- **The range is derived, never stored.** A chapter runs from the start of its first step
  to the end of its last, so one chapter may span several steps and a step may carry none.
  `src/plan/chapters.mjs` (CLI) and `web/lib/planChapters.ts` (watch page) implement the
  same derivation, checked against one fixture (`test/fixtures/plan/spool-chapters.json`).
- **Additive.** A timeline recorded before chapter anchors keeps its exact shape, produces
  no ranges, and seeks by step as it always did.
- **Clocks.** `timeline.json` ranges are on the recording clock; `share/spool.json` ranges
  are on the output clock; the watch page divides by `rate` to reach the `final.mp4` clock
  it seeks. A range boundary is always a window boundary, so a seek lands on the chapter's
  first frame.
- **Validated at authoring time.** An unknown chapter ID fails `spool lint` and the record
  harness, and returns `400` from `POST /step` — a typo would publish a plan summary item
  that seeks nowhere. `spool lint` also warns when a chapter of `plan.script.json` has no
  recorded step (check `plan-chapters`).

### share/plan.json (published copy)

`spool share` writes the published copy of the packet beside the media, and copies
`evidence.json` when the workdir has one:

```
spool/<slug>/share/
├── plan.json          # the packet, canonicalized and self-contained
└── evidence.json      # the descriptors, resolved: redacted, pinned, degraded
```

`share/plan.json` is `plan.json` with `chapters` resolved to their effective list,
`alternatives` normalized to an array, `risks` normalized to claims
(`{"claim": "…", "evidence": [], "chapterId": null}`), and the resolved evidence
descriptors embedded under `evidence`. The copy is deterministic: the same packet
always serializes to the same bytes.

`share/evidence.json` carries the **resolved** descriptors, not the authored file.
Resolution happens once, here, so no consumer can read the raw version by mistake:

- every published string is **redacted** — URL credentials, `key=value` and
  `Bearer` secrets, provider token shapes (`ghp_`, `sk-`, `xox…`, `AKIA…`, JWTs,
  private keys) and home directories become `[redacted]`;
- `url` is built only when it can be **pinned and trusted**: a GitHub blob URL at
  `revision` or `links.commit` (with `#L<start>-L<end>` when `lines` is set), a
  commit URL, or a sanitized `http(s)` URL. Every path segment is
  percent-encoded, so a ref cannot add a query, a fragment or a path of its own;
- `excerpt` is `{"text": "…", "truncated": bool, "redacted": bool}` or `null`.

Every published descriptor carries a `status` and a `reason`, which is how missing
and private evidence **degrades instead of breaking**. A renderer switches on
`status` and never has to handle an error case:

| status | what the bundle carries | what a renderer shows |
| --- | --- | --- |
| `available` | `url`, or an `excerpt`, or both | the link and the label |
| `unpinned` | `ref`, `url: null` | the ref as text, marked not pinned |
| `missing` | `ref`, `url: null` | the label, marked not found in the checkout |
| `private` | label, kind and `chapterIds` only | the label, marked withheld |

`missing` is only published when the workdir sits inside a git checkout and the
ref did not resolve there. Without a checkout the state is unknown, and unknown is
never published as missing.

`share/spool.json` gains a `plan` pointer when the workdir is a Plan Spool
(absent otherwise, so v1 bundles are byte-identical):

```json
"plan": {
  "file": "plan.json",
  "evidenceFile": "evidence.json",
  "version": 1,
  "goal": "…",
  "outcome": "…",
  "chapters": [{"id": "context", "title": "What exists today"}],
  "currentState": [],
  "approach": [{"id": "data", "summary": "…", "chapterId": "approach"}],
  "alternatives": [],
  "noAlternativesReason": "…",
  "assumptions": [],
  "risks": ["…"],
  "decision": {"type": "approval", "prompt": "…", "options": ["approve"]},
  "evidence": [],
  "links": {"repo": "aaarnv/spool", "commit": "abc1234"}
}
```

The block repeats the published packet's static proposal, so the watch page renders a
plan in one fetch, and points at `plan.json` / `evidence.json` for the full copy. It
never carries the mutable decision status: that lives in the database, so an immutable
blob can never contradict it. The lineage ids above are additive on the same block.

`spool read` prints the plan digest (goal, outcome, approach, alternatives, risks,
decision, evidence) above the per-step narration, so a receiving agent gets the
decision packet without watching the video.

`spool publish` ships both files to the host, where they are stored as
`spools/{id}/src/plan.json` and `spools/{id}/src/evidence.json` (see
[Publish](#publish-two-calls)). The watch page needs neither fetch — the `plan` block
above already carries the summary and the resolved descriptors — so they exist for the
agent that reads the full copy, and for the completing call that opens the lifecycle
from the packet the server itself stored.

Cloud renders (`spool finish --cloud`) do not carry the packet yet: the upload
grants are issued per known source file, so the worker's bundle has no
`share/plan.json`. Publish a Plan Spool locally until the hosted publish path
accepts the packet. The pre-upload gate still validates it, so an invalid plan
never reaches the worker.

`templates/plan.json` and `templates/evidence.json` are the authoring starting
points; `spool plan init` is how you get a copy of them. Contract tests: `npm test`
(`test/plan-schema.test.mjs`, `test/plan-evidence.test.mjs`,
`test/plan-json-schema.test.mjs`, `test/plan-workdir.test.mjs`,
`test/plan-cli.test.mjs`, `test/plan-generate.test.mjs`,
`test/plan-generate-cmd.test.mjs`, `test/plan-publish.test.mjs`,

## Render layer inputs

`spool render <workdir> [--preview]` reads `timeline.json` +
`vo/manifest.json`, runs the normalize pass (`video.webm` → `video.mp4`, CFR 30fps, H264,
yuv420p, +genpts), then renders one ffmpeg filtergraph (1920x1080 canvas, recording on a
near-full-bleed rounded card, subtitle-style intro title, captions/VO/zoom on the OUTPUT
clock below). Every layer that is not footage — card chrome, caption pills, plan cards,
hook/CTA, cursor, ripple — is screenshotted once by Playwright from the same CSS the
product uses, then composited by ffmpeg with time expressions. Output rate defaults to
60fps, and is stamped into `render.json` so the share layer rebuilds the same windows.
`SPOOL_RENDER_FPS` overrides it (30 halves the frame count and the render cost).

**Background canvas.** There is no flag for it: the canvas is house-picked, and `SPOOL_BG`
is the escape hatch for one local render. A spec resolves in this order:
1. **repo preset** — `graphite` (dark neutral), `paper` (light warm), or `indigo` (brand
   gradient, the default), each a shipped `assets/bg-<preset>.jpg`;
2. **macOS wallpaper** — any still under `/System/Library/Desktop Pictures` by name
   (case-insensitive, spaces→dashes: `sonoma`, `"Sonoma Horizon"`, `sonoma-horizon`).
   Resolved at RUNTIME on the author's Mac — never shipped (Apple copyright). HEIC is
   converted to JPG via `sips` and cached under `~/.spool-cache/bg/<name>.jpg`;
3. **image path** — any file on disk;
4. **fallback** — the repo default (`indigo`) when a spec resolves to nothing (e.g. a macOS
   wallpaper name on a non-Mac).

The resolved image is staged into the workdir as `.spool-bg.jpg` and composited full-bleed
with `objectFit: cover`, rasterised once into the background layer (so it is present from
frame 0 — no load flicker). The bg name is stamped into `render.json` (`bg` field) alongside `rate`. On publish the resolved
`.spool-bg.jpg` uploads as `spools/{id}/src/bg.jpg` so the Linux edit worker can re-render
the same canvas (see docs/EDIT-CONTRACT.md).

**Vertical format (`config.format`, from `spool live --format vertical`).** The canvas becomes 1080x1920.
The capture itself is unchanged and is never letterboxed: a virtual camera cover-crops the
landscape recording onto a rounded stage, then pans and zooms to follow that step's clicks
(`zoom: "auto"`) or drifts gently across it (`"none"`), cutting hard at every step boundary.
Over that stage sit a hook card for the first ~2s, big burned-in word captions, a music bed
ducked under the voice, and a CTA card over the last ~1.5s. Because the crop upscales the
capture, author vertical spools with a 1920x1080 `viewport`. Wide renders are unaffected.

**Plan visual templates.** A workdir with both `plan.json` and `plan.script.json` adds the
plan artifacts to the render's input props. `evidence.json` is optional. The renderer
converts the packet into six stable card types:

| Card | Source |
| --- | --- |
| context | `goal` and `currentState[].claim` |
| outcome | `outcome` |
| sequence | `approach[].summary` in declared order |
| risks | `risks[]` and `assumptions[]` |
| decision | `decision.prompt` and its ordered options |
| evidence | descriptor `label`, `kind`, and bounded `ref` only |

A chapter whose `plan.script.json` visual kind is `browser`, `code`, `image`, or `terminal`
uses **overlay mode**. Overlay mode reserves separate rectangles for the recording, plan
card, evidence attribution, and word captions. The rectangles never overlap. Browser and
OS recordings use the same media rectangle and keep their source aspect ratio. A `card`
visual, a missing visual, or a chapter with no usable source uses **card-only mode** and
does not paint the recording under the card. Both modes derive their bounds from the
output canvas and support 1920x1080 and 1080x1920 outputs.

One token module owns typography, color, geometry, and motion. R2.2 carries three founder
review directions: `editorial-minimal`, `technical-system`, and `warm-briefing`.
`config.planTheme` wins over a prior `render.json.planTheme`. Founder review selected
`warm-briefing` as the product default on 2026-08-13. The resolved ID is stamped into
`render.json` for identical worker re-renders.
Re-renders must also carry the three plan artifacts because the theme alone has no plan
copy to paint. An ordinary workdir without `plan.json` receives no plan props and keeps
the prior layout and render stamp shape.

**`render.json`** (written by `spool render`, and re-read by the Fly edit worker so a
re-render matches):

```json
{ "rate": 1,
  "bg": "indigo",
  "format": "vertical",
  "planTheme": "technical-system",
  "vertical": { "hook": "Your diffs explain themselves now",
                "cta": { "text": "See the full walkthrough", "url": "spoolkit.dev" },
                "music": "uplift" } }
```

`planTheme` is written only for a plan workdir. `vertical` is written only when `format` is
`vertical`. Both snapshot resolved authoring fields, so a worker re-render with no
`steps.mjs` in the workdir frames the output identically.

**`layers/fg.webm`** (written beside `final.mp4`, and recorded in `render.json` as
`"fg": "layers/fg.webm"`). The same composite as `final.mp4` with the wallpaper left out:
card chrome, footage, cursor, ripples, zoom/pan, captions and the vertical hook/CTA, in VP9
with alpha at the render's fps. It is a second output of the one filtergraph, so the
footage is decoded and zoomed once for both. Audio lives in `final.mp4` only.

The layer exists so a background change is one overlay pass (`src/render/bg-swap.mjs`)
instead of a re-render — the flattened result measures SSIM 0.997 against a full render of
the same take. It is skipped for plan workdirs (no wallpaper to swap), previews, and
`--rate` takes (the layer would need the same speed pass); those keep re-rendering. Decode
it with `-c:v libvpx-vp9`, since the default vp9 decoder drops the alpha channel.

**Retiming (record-first).** The capture is natural-speed; the renderer maps each step
onto an output window and concatenates them from t=0:

- `window_i = max(voDuration_i + 0.4, recordedDuration_i)`, `outStart_i = Σ_{k<i} window_k`.
- Video: the step's recorded slice (`[start_i, end_i]`) plays at **1x** at `outStart_i`,
  then its **last frame freeze-holds** for the rest of the window (window is a max, so the
  played portion always fits; video is never sped up). A ~1s tail holds the final frame.
- Audio: `vo seg_i` is placed at `outStart_i`. Captions offset each segment's word times by
  `outStart_i`. A click logged at recording time `t` in step `i` maps to `outStart_i + (t − start_i)`.

The rate is **1.0** and there is no flag to change it: pacing is narration-driven, and dead
air in a window is a freeze under continuing narration. The web editor's `set_rate` op is
the one writer of a different rate; when it sets `rate ≠ 1` the worker speeds the whole clip
(video setpts + pitch-preserved atempo) → `final.mp4`, which then runs on a compressed clock.

A step's `chapterId` rides onto its output window unchanged, so a renderer layer can key a
plan card off the window it belongs to (see "Plan Spools" → "Chapter mapping").

Bookkeeping: `video.mp4` and all times in `timeline.json` / `console.jsonl` stay on the
**recording** clock; `spool.json` step `start`/`end`/`clicks` and `duration` are on the
**output** clock. `spool share` extracts keyframes from `video.mp4` (recording clock) but
reports output-timeline step times, `duration` from `final.mp4`, and a top-level `rate`.

Rendered layers are written to `<workdir>/.spool-ffmpeg/` and deleted when the render
succeeds; `SPOOL_FFMPEG_KEEP=1` keeps them, along with the filtergraph that ran, for
debugging. Encoding is two-tier and the tier follows the purpose, not a flag: a `--preview` draft gets
ultrafast x264 crf 28, and every `final.mp4` gets libx264 `-preset slow -crf 17` under
`nice`. Hardware H264 (VideoToolbox) remains the fast path a box can offer, and a box
without it always gets libx264 — which is what the Linux worker runs.

## Cloud render (`spool finish --cloud`)

`--cloud` hands a recorded take to the hosted worker: VO, render, share bundle and publish
all happen server-side and the CLI prints the watch link. It needs a capture (`video.webm`
or `capture.mp4`, plus `timeline.json`) and a connected account, but no local `vo/`.
`spool render --cloud` runs the same job (a cloud render is a finish with no local work).
`--no-publish` and `--preview` are errors: a cloud job's product is a published link, and a
preview is by definition a local draft.

The CLI's only local work is the normalize pass (`video.webm`/`capture.mp4` → CFR
`video.mp4`, the file the worker renders from) and the upload:

1. `POST {host}/api/render-jobs`, Bearer publish token, body `{ title, duration: null,
   payload: { rate, bg, hq, voice, speed, format }, sources: { hasBg, hasConsole } }`.
   `payload.bg` is the RAW spec (flag, `SPOOL_BG`, or prefs), not the resolved tag. Returns
   `{ id, jobId, url, uploads: [{ pathname, contentType, token }] }`. `402` (free cap, carries
   `upgradeUrl`) and `429` (plan cap) print and exit 1 with nothing uploaded.
2. One PUT per grant to Blob with the scoped token (`x-api-version: 10`,
   `x-add-random-suffix: 0`, `x-allow-overwrite: 1`), the same write the worker itself makes.
   The source set is `spools/{id}/src/{timeline.json,render.json,video.mp4}`, plus `bg.jpg`
   and `console.jsonl` when the workdir has them.
3. `POST {host}/api/render-jobs/{jobId}/start` flips the job from `uploading` to `queued` so
   nothing enters the worker's poll half-uploaded.
4. `GET {host}/api/render-jobs/{jobId}` every 5s until `status` is `done` (prints the watch
   url on stdout and writes `share/published.json`, so `spool open` reopens it) or `error`
   (prints the worker's error, exit 1). Gives up after 30 minutes; the job may still land, so
   the link is recoverable with `spool list`.

Two inputs the CLI resolves so the worker does not have to:

- **`timeline.json`** ships with per-step `narration`. Live takes already carry it; a scripted
  workdir keeps its narration in `steps.mjs`, which the worker never sees, so the CLI folds it
  into the uploaded copy. The workdir file is never modified.
- **`render.json`** ships the render intent: the same `{ rate, bg, format, vertical }` stamp a
  local `spool render` would write, resolved identically (`steps.mjs` config > prior
  `render.json` > defaults). Because bg presets round-trip by name, only a macOS wallpaper or
  a custom image path uploads `bg.jpg`; a preset is re-resolved on the worker.

## Merged-PR recaps (`render_recap`, roadmap B2)

A team that never runs the CLI still merges pull requests. A recap is what spool makes of
one, by itself: when a merge lands on an opted-in repository, the platform reads the diff
from GitHub, authors a script and its diagrams, renders a vertical video and publishes it
as an ordinary spool with the repo's identity. No author machine, no capture, no agent.

**Enablement is a deliberate act, per repository.** `repo_feeds.recap_enabled` (default
`false`, migration 0024) is what turns it on, and it is NOT implied by `feed_enabled`:
opting a repo into the feed says where its spools appear, while this says the platform may
READ that repo's diffs and spend a render on every merge. The row's `enabled_by` is the
owner every recap spool belongs to, and whose `caps.cloudPerMonth` it spends —
`platformRendersThisMonth` counts recaps beside the CLI's cloud renders, because they run
the same worker.

**The pipeline**, one step per boundary:

1. `POST /api/github/webhook` verifies the signature, records the delivery as plan events,
   then offers it to `recapOnDelivery` (web/lib/recapEnqueue.ts). Only a `pull_request`
   `closed` + `merged: true` delivery is considered — the same `mapDelivery` translation
   the event stream reads, so a merge means one thing in this codebase. Neither step can
   fail the other, and the recap half never throws: a hook GitHub disables costs the plan
   event stream too.
2. The enqueue reserves a spool row (repo identity, `format: "vertical"`, the visibility
   `resolveVisibility` gives it) and inserts a `queued` `edit_jobs` row of kind
   `render_recap`, then wakes the worker. The payload names the pull request and never
   carries it: `{ rate, bg, voice, speed, format, repoOwner, repoName, prNumber }`.
3. The worker claims it through the same lease queue, asks
   `POST /api/edit-jobs/{id}/github-token` for an installation token scoped to the job's
   own repository, fetches the pull request, authors, renders, and uploads through the
   same blob grants every platform render uses.
4. `PATCH /api/edit-jobs/{id}` with `done` fills in the spool's title and duration and
   marks it source-bearing, exactly as for a `render`/`render_packet`. It does NOT open a
   plan lifecycle: a recap is not a proposal.

**Two doors, one enqueue.** Besides the webhook, `POST /api/actions/v1/dispatch` is the
server side of the public action's `notify` mode (public-action/scripts/dispatch.mjs) —
for teams whose repositories the GitHub App is not installed on, or who would rather
trigger from their own workflow. Bearer auth with a publish token:

```json
{ "event": "pull_request.merged", "repository": "aaarnv/spool",
  "ref": null, "sha": null, "runUrl": null,
  "payload": { "action": "closed", "number": 41, "pull_request": { "number": 41 } } }
→ { "id": "<spoolId>", "url": "https://…/l/<spoolId>", "jobId": "<uuid>" }
```

`payload` is the raw GitHub event, so `${{ toJSON(github.event) }}` is enough; `number`,
`pull_request.number` and a hand-written `prNumber` are all read. `pull_request.merged` is
the only event that renders anything today and every other event is refused BY NAME rather
than ignored, so a workflow asking for something this host cannot make is told so.

Both doors run the same `enqueueRecap` under the same gates, because an event arriving
over a signed webhook and the same event arriving from a workflow must produce the same
recap under the same rules. What the route adds is only WHO IS ASKING, and it needs two
credentials that agree: the token proves an account, `recap_enabled` proves the platform
may read that repository, and the token's owner must BE the account that enabled recaps
there. Without that last check a token holder could name any repository and spend a
stranger's render budget reading code they have no claim to.

Statuses are chosen against the action's own error vocabulary: `401` a bad token, `403`
recaps not enabled (or enabled by somebody else), `429` over the monthly render cap, `400`
a malformed or unsupported request. A re-run answers `200` with the recap that pull
request already has plus `alreadyQueued: true`, because a repeated workflow run is not a
failure. `402` is never returned — the free publish cap is an upgrade prompt shown to a
PERSON at the moment they publish, and there is no person in a workflow run.

**One recap per pull request, ever**, enforced by a unique index over the payload's
`repoOwner`/`repoName`/`prNumber` (`edit_jobs_one_recap_per_pr`) rather than by a read.
GitHub redelivers on demand and a PR can be reopened and merged again, so the check has to
hold across a retry rather than inside one request. It is deliberately not partial on
status: a recap that already errored is not re-enqueued by a redelivery either, because a
job that failed twice on its own will fail a third time and a webhook must not be able to
spend renders in a loop. Recovery is the operator's, not the hook's.

**The diff is bounded before the model sees it** (src/recap/pr.mjs): 40 files, 6KB of
patch per file, 60KB across all files, 30 commit subjects, 4000 characters of description.
Per-file first and total second, in that order — trimming the total alone would spend the
whole budget on whichever file GitHub listed first. Everything dropped is stated in the
prompt under "WHAT YOU ARE NOT SEEING", because a script written from a partial diff has
to know it is partial.

**Authoring** reuses the packet stages (src/recap/author.mjs). The script prompt is new
(`src/packet/RECAPPER.md`: why / what changed / worth knowing) and runs behind the same
`sloplint` gate; the diagram stage is `DIAGRAMMER.md` unchanged, because it reads BEATS
and never the packet, so it cannot tell a plan's beats from a recap's. The visual layer is
always `diagram`. The render is `renderAuthoredVideo` (src/packet/video.mjs) — the one
copy of the VO → comp → share chain, shared with `render_packet`.

**The worker holds no GitHub App key.** `POST /api/edit-jobs/{id}/github-token` (worker
secret + the running job's lease) mints an installation token for the repository the JOB
names — the worker cannot ask for a repository it was not given, because it names none in
the request. Same reason it holds no standing Blob token: a render box a webhook can start
is the worst place to keep a credential that writes to every installed repository. It
answers `409 { error: "no_installation" }` when the App was uninstalled between the merge
and the render, and `403` for any job kind that is not `render_recap`.

## GitHub App (webhooks → plan events, gate status, merge)

Everything spool writes to GitHub has two possible writers: the agent's `gh` CLI, and the
Spool GitHub App. The CLI path is unchanged and is the default. Registration, permissions and
the environment are docs/GITHUB-APP.md; this section is the contract the App adds.

`POST /api/github/webhook` verifies `x-hub-signature-256` over the RAW body, then appends one
`plan_events` row per plan spool whose `spools.pr_number` names the delivery's pull request.
The rows reach agents through the same cursor as every other event (`GET /api/events`).

| delivery | `type` | payload |
| --- | --- | --- |
| `check_suite` completed | `github.ci_status` | `source: "check_suite"`, `state`, `sha`, `context` |
| `status` success/failure/error | `github.ci_status` | `source: "status"`, `state`, `sha`, `context`, `description` |
| `pull_request_review` submitted | `github.review` | `state` (lowercased), `reviewer`, `commitSha` |
| `pull_request` closed+merged | `github.pr_merged` | `mergedBy`, `mergeCommitSha`, `mergedAt` |
| `pull_request` closed | `github.pr_closed` | `headSha`, `baseRef` |
| `pull_request` synchronize/reopened/ready_for_review | `github.pr_updated` | `action`, `before`, `after` |

Every payload carries `version`, `deliveryId`, `repo` and `prNumber`. Pending statuses and
in-progress check suites are dropped. The idempotency key is `gh:<delivery-id>`, so GitHub's
redelivery writes nothing. Actor is `system`.

`POST /api/plans/{spoolId}/merge` (capability `plan.merge`, owner session only) adds
`github.merge_requested` before the merge is attempted, `github.merge_result` after it, and
`github.merge_refused` when the gate blocked the tap — keyed by cause and head commit, so a
repeated tap records the cause once. Refusals are typed tokens —
`plan_not_approved`, `proof_missing`, `proof_unwatched`, `proof_not_watched_here`,
`pr_not_mergeable`, `head_moved`, … — with 409 and, where it helps, `proofSpoolId` and
`viewerDays`. The gates are the plan's policy (advisory/required, as for implementation) and
the proof-watched rule, both defined in docs/GITHUB-APP.md §4.

`POST /api/github/gate` publishes a gate verdict as the `spool/plan-gate` commit status — the
same context src/gate/status.mjs posts, so one branch rule covers both writers. It answers
`409 { reason: "no_installation" }` when the App covers nothing on the repository, which is
the signal to post with `gh` instead.
